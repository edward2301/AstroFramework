SECTION 00

结论先行

五条判断，先说清楚，后面再论证。

判断结论理由
soukacatv 的架构思路值得全盘学 值得 双轴信息架构（品类 13 + 场景 5）+ CPT 化内容模型，是它撑住 462 页还保持清晰的根本原因。这套思路与 CMS 无关，换成任何技术栈都成立。
它的工程实现不要学 反面 Title 达标率 21%、Product schema 0/88、227 页无页面级实体、图片尺寸覆盖 0.37%、HTML 零缓存头。全部是「用默认配置代替按价值分级配置」的后果。
Astro 静态产物 + Cloudflare Pages 是唯一部署形态 推荐 构建期产出纯文件，Pages 负责全球边缘分发、自动 HTTPS、预览部署与按版本回滚。没有服务器要打补丁、没有证书要续期、没有站点配置文件要覆盖同步。
交互数据落 D1，Wrangler 是唯一读写入口 数据 询盘与运营记录存 Cloudflare D1（SQLite 兼容的 SQL 库），运维用 wrangler d1 execute 写入与查询、wrangler d1 export 导出备份。站点代码不连库，表单仍是纯前端 mailto。
路由规则随产物走，不写在服务器里 规则 缓存头、404 直访、旧链接 301 由 public/_headers 与 public/_redirects 承担，构建时复制进 dist/，与页面同版本发布、可回滚。
一句话概括：soukacatv 证明了「这套内容架构在 B2B 工业品出口领域跑得通」，同时证明了「用默认配置去承载它，工程层会全面失守」。你要做的是继承前者、替换后者——把每个环节都变成构建期强制校验，把部署与数据收敛到 Cloudflare 一套托管服务里。
SECTION 01

那套方案该学什么、不该学什么

按「架构 / 内容 / 工程」三层拆开看，每层的结论完全不同。

层次对象结论实测依据
架构 双轴分类模型学 品类轴 13 个（3 一级 + 10 二级）覆盖「我要买什么」，场景轴 5 个方案覆盖「我要解决什么问题」。两种搜索意图各有落点，经 sitemap 与导航双重验证成立
CPT 化内容模型学 product / product_cat / solution / case / faq / download / video 各自独立，而非全塞进「文章」。这是 462 页仍结构清晰的根本原因
sitemap 按类型拆分学 9 个独立 sitemap 各有 lastmod，便于分类型监控索引率
URL 平铺根目录不学 462 个 URL 中 450+ 是一级路径，产品、FAQ、博客、案例全在同一层级，靠 slug 区分。扩到 2000 页会失控
内容 品类页内容密度学 抽样 3 个品类页实测 3,747–4,221 词，含应用场景、选型逻辑、参数对比维度
FAQ 长尾矩阵学 194 个问句式页面独立成页，覆盖「how many / can I / what is」类长尾。是它最有价值的资产
公司通稿混入博客不学 118 篇中约 44 篇为节日/展会/沙龙稿（37%），稀释了博客的主题集中度
工程 元标签人工填写不学 无任何长度校验，全站 Title 达标率仅 21%，FAQ 最长 124 字符，下载页 13/14 短于 30
schema 按 CPT 一刀切不学 Product 0/88、FAQPage 0/194、ItemList 0/13；227 页只有面包屑，无 WebPage / Organization
图片交给主题处理不学 7,492 张图中仅 0.37% 有 width 属性，1.55% 有 lazy

最重要的一课，不在上表里：它的缺陷几乎全部来自同一个动作——把「系统默认」当成「配置完成」。Rank Math 装了、CPT 建了、CDN 上了，每一项都"做了"，但没有一项按页面价值去分级配置。

这意味着：换 Astro、换托管平台都不会自动解决这个问题。真正要继承的是「每个环节都要有强制校验」这个习惯。
SECTION 02

核心思路拆解

六条可以直接迁移到任何技术栈的设计原则。

2.1 双轴：产品轴 × 场景轴

B2B 工业品的搜索意图天然分成两类，必须用两套 URL 承接：

意图用户在想什么对应的页面类型示例
产品轴「我需要一个 X 设备，参数要满足 Y」品类页 → 产品详情页/products/digital-modulator/ → /products/skd2618/
场景轴「我要做一个酒店电视系统，怎么配」方案页（跨品类组合）/solutions/hotel-iptv/

这两轴的价值在于：同一批产品可以用两种方式被搜到。搜「QAM modulator」的人落到品类页，搜「hotel IPTV system design」的人落到方案页，两条路径最终都指向同一组产品，但切入的意图完全不同。

2.2 内容模型先行，页面模板后置

它把内容拆成 7 类独立实体（产品 / 品类 / 方案 / 案例 / FAQ / 下载 / 视频），而不是「文章 + 分类」。这个决定的价值在两年后才显现：

  • 每类实体可以有自己的字段（产品有型号、MOQ、认证；案例有酒店名、房间数、交付时间）
  • 每类实体可以有自己的模板与 schema
  • 每类实体可以有自己的 sitemap 与索引策略

2.3 用长尾问答铺满采购决策链路

194 个 FAQ 页面覆盖的是采购过程中真实会问的问题：How many hotel televisions can receive one modulated channel?、Can an analog modulator work with an existing coaxial network?。这类问题的搜索量单个不大，但数量足够多、意图足够精准。

但它把这条策略做废了：194 个 FAQ 页之间互不相链，也没有链回产品与方案页，内链数在所有页面恒为 45（全部来自导航与页脚）。等于 194 个孤立节点。这是你必须在第一天就设计好的部分。

2.4 内链靠字段而非手写

它的博客做了完整的 Related 模块——每篇文章固定输出 Related Products ×3、Related Solutions ×3、Related Blogs ×3。这个做法本身是对的（用字段关联而非手工插入链接），问题出在案例页：三个不同酒店的案例链出的 6 个产品完全相同，说明关联字段被硬编码了。

2.5 内容密度是护城河

品类页 3,747–4,221 词（抽样 3 页），方案页 3,662 词（抽样 1 页）。这个量级在工业品出口站里属于上游。它的价值不在「字数」本身，而在于把选型逻辑、适用场景、参数对比维度都写在页面上——这正好是 AI 搜索时代最容易被引用的内容形态。

2.6 反面：工程层全线缺位

这一条单独列出来，因为它是本方案要重点解决的问题。第 5 节的落地要点几乎全部由此而来。

SECTION 03

技术组合适用性评估

四个组件各管一层，职责边界写死，不多做一件事。

3.1 Astro：与需求高度匹配

直接消除的缺陷

  • 零 JS 默认输出 —— 不会有主题自带的一堆渲染阻塞脚本
  • 内容 schema 在构建期强制校验 —— 字段缺失当场中断，不会带着空洞上线
  • 目录式产物 + 尾斜杠统一 —— 一个页面只有一个 URL

不会自动带来的东西

  • 标题长度与唯一性 —— 由 scripts/validate-content.mjs 强制
  • Schema 按页面价值分级 —— 由 lib/seo/schema.ts 显式写
  • 缓存头与 404 规则 —— 由 public/_headers / _redirects 显式写

项目保持 output: static，不引入 adapter、不开 SSR：页面在构建时就全部渲染完，请求路径上不存在任何服务端逻辑。

3.2 Cloudflare Pages：静态产物的原生落点

能力在本方案里的作用
全球边缘分发dist/ 直接铺到边缘节点，不存在回源延迟；静态资源带 hash，命中率接近 100%
自动 HTTPS证书签发与续期由平台承担，不需要自签证书、不需要手工配置 TLS 参数
预览部署与回滚每次部署是不可变版本，--branch 生成独立预览 URL；出问题在控制台一键回滚
配置文件随产物_headers / _redirects 与 HTML 同版本发布，规则变更可随部署一起回滚，不会出现「代码与部署规则不同步」
构建集成连接 Git 仓库后自动跑 npm run build，构建守卫（内容体检 + 链接检查）在每次部署都执行
硬约束：不要配 SPA fallback，不要写 /* /index.html 200 这类通配兜底。目录式产物里没有登记的路径必须返回真 404，否则每个错误 URL 都会变成首页副本被大量收录。

3.3 D1 + Wrangler：交互数据的存取

交互数据（询盘、运营记录）存 Cloudflare D1，这是 SQLite 兼容的托管 SQL 库。读写只走 Wrangler CLI：

运维 / 运营人员
按表单字段整理记录
Wrangler CLI
d1 execute（写 / 查）
d1 export（备份）
Cloudflare D1
inquiries 表
--remote 线上 / --local 本地
站点静态产物不连库，两条链路互不干扰
Cloudflare Pages
纯静态页面与表单
访客浏览器
mailto 生成邮件草稿
邮箱
销售收到询盘
为什么这条链路没有性能风险：写入是运维按需执行的离线操作，不在访客请求路径上。因此不存在连接池被打满、同步写库阻塞、后台报表与写入争抢 IO 这类问题，也不需要异步批量或消息队列来做削峰。

Wrangler 配置集中在仓库根目录的 wrangler.toml：name / pages_build_output_dir / compatibility_date 管部署，[[d1_databases]] 声明数据绑定。database_id 首次 wrangler d1 create 后回填。

3.4 安全与合规分层

层面由谁承担
流量型攻击 / DDoSCloudflare 边缘网络，带宽型攻击在到达站点前就被吸收
应用层访问控制Cloudflare WAF 与自定义域规则；不需要维护回源白名单或站点防火墙规则，因为没有自管服务器
凭证管理本地 wrangler login；CI 用 CLOUDFLARE_API_TOKEN / CLOUDFLARE_ACCOUNT_ID 环境变量，不进仓库
客户数据D1 内，按周期 d1 export 导出到受控位置；导出的 .sql 含客户信息，禁止提交进仓库
不要让 404 页、sitemap 与 robots 进入长缓存——前者会把一次错误响应固化，后者会让新页面迟迟不被发现。三者已在 _headers 里按路径显式设为 no-store；HTML 页面沿用 Pages 默认缓存，不额外配置规则。

3.5 这套架构对 SEO 的影响面

SEO 要求落地位置

一个页面一个 URLtrailingSlash: 'always' + 目录式产物，Pages 自动补齐尾斜杠
404 页不被收录页面本身 noindex；404 产物 no-store；直访 301 到首页
分语言错误页Pages 按语言前缀就近查找 <前缀>/404.html；构建守卫按 LOCALES 从 <前缀>/404/index.html 复制
新页面及时被发现sitemap / robots 不缓存；lastmod 取源文件最后提交时间（Git 集成构建需完整历史）
canonical / hreflang 一致域名唯一来源是 astro.config.mjs 的 site

4.2 为什么不选自托管

对比项Cloudflare Pages + D1（选定）自托管服务器 + 自建数据库
起步速度半天 创建项目、建 D1 表、部署2–3 天 装环境、配站点、调证书与缓存
运维负担近乎为零 无补丁、无证书续期、无日志轮转需专人 系统升级、配置漂移、监控告警
性能上限极佳 产物直接在边缘，无需回自建服务器好 需要调优缓存与服务器参数
数据落点Cloudflare D1，Wrangler 读写与导出自托管数据库，需自行备份、扩容、限流
故障面只有平台与配置两个变量服务器、站点配置、数据库、缓存层都可能出问题
规则一致性强 路由规则与页面同版本发布、可回滚弱 配置独立于仓库，改代码与改配置容易不同步
选定结论：交互数据不要求落在自托管数据库，D1 + Wrangler 完全够用，因此没有理由为一台自托管服务器付出长期运维成本。判断标准只有一条：数据最终要存在哪里、谁要读它。

4.3 运行期能力的边界

wrangler.toml 已配置 [[d1_databases]] 的 binding = "DB"，但当前静态产物不读取它——交互数据只由运维通过 Wrangler CLI 写入与查询。

若将来要让表单自动入库，才需要引入 Pages Functions 承接 POST 并使用这个 binding，同时补人机验证与限流。这一步不在当前方案范围内：站点保持纯静态构建、无运行期服务端，内容模型与校验链路均不改动。

SECTION 05

关键环节落地要点

十项。目标是让第 1 节列出的工程缺陷在新架构里不可能再发生。

5.1 URL 与路由：用目录把层级写死

所有 URL 末尾带斜杠（trailingSlash: 'always'），产物是目录式 /path/index.html。Pages 默认的 auto-trailing-slash 会自动补齐缺斜杠的请求，不产生重复 URL。旧链接 301 在 _redirects 里用精确路径逐条登记，不要用正则或通配，避免误伤正常页面。

5.2 内容模型：用 schema 卡住字段

内容集合的 schema 集中在 src/content.config.ts：型号必须有 5 项关键参数、品类 intro 不少于 300 字、译文 intro 不少于 150 字。draft: true 的条目不生成路由、不进列表；已发布条目引用草稿会在体检阶段报错。

5.3 元标签：三段式模板 + 构建期体检

标题与描述阈值读 src/data/site.ts 的 SEO_LIMITS，按显示宽度计（全角计 2）。标题全站唯一，内容里的 seoTitle 只写标题本体，后缀由 lib/seo/branding.ts 单点拼接。区间下限不是排版偏好，而是信息完整度的代理指标——低于下限通常意味着少了量程、精度或认证中的一项。

5.4 Schema：按页面价值分级

品类页、型号页、FAQ 页、案例页各有自己的结构化数据，不做「一刀切套同一个类型」。每页唯一 <h1>，每个内容页有可见面包屑，且面包屑组件与 breadcrumbSchema 共用同一个 crumbs 数组。

5.5 图片管线：显式声明尺寸

图片放 public/images/…，由运营同名维护；任何 <img> 必须带 width / height / alt / loading，由校验脚本扫描（扫描前先屏蔽注释）。构建时不处理图片，避免引入图片服务依赖。

5.6 缓存与边缘：一份配置说清楚

规则全文以 public/_headers 为唯一来源（随 dist/ 发布），本节只记设计约束，不复制内容：

  • 带 hash 的构建资源长缓存一年；404 产物、sitemap 与 robots 一律 no-store；HTML 沿用 Pages 默认缓存，不额外配置
  • 只写 Cache-Control、不叠加 expires；同一路径被两条规则匹配时响应头会合并（如 no-store, no-store），故 sitemap 只保留通配 /sitemap-*.xml 一条
  • deploy/cloudflare/README.md 第 6 节列出规则清单与逐条作用，改规则时两处同步

5.7 表单与询盘：静态站不必强行接后端

询价页是纯前端表单：必填项与邮箱格式校验、防重复提交，然后按 data-mailto 组装邮件草稿；没有默认邮件客户端时，页面保留可复制的询价内容与备用邮箱地址。

数据怎么进 D1：由运维把收到的询盘按字段整理，用 wrangler d1 execute … --command "INSERT …" 录入或批量 --file 导入。表单不会自动写入 D1，站点代码也没有任何数据上报逻辑。这条边界要写进运维手册，避免误以为「上线即有线索库」。

5.8 交互数据链路：D1 表 + Wrangler 读写

D1 表 inquiries 存放询盘记录。表单的 name 字段存为 contact_name（列名避免与其它「名称」混淆），另加 id / created_at / locale / source / status 由默认值或运维填充。建表语句、字段映射表与全部读写命令以 deploy/cloudflare/README.md 第 2、4 节为唯一来源，本文不复制 SQL 或命令清单。

能力设计要点
保存wrangler d1 execute --remote；写入是运维按需执行的离线操作，不在访客请求路径上
读取SQL 条件查询，可加 --json 交给脚本处理
演练--local 落在 .wrangler/（已忽略），不碰线上库
备份wrangler d1 export 周期性导出；Pages 部署回滚不含数据，需单独按备份恢复
纪律：带 --remote 才是线上库；导出的 .sql 含客户邮箱与公司名称，禁止提交进仓库（.gitignore 已忽略 *.sql）。

5.9 多语言：起步就预留，别等以后再改

语言与路径映射只有 src/i18n/routing.ts 一个来源，Astro 与 sitemap 的 i18n 配置直接导入它的常量。新增语言时 [lang]/404.astro 按 LOCALES 自动产出该语言 404，构建守卫 build-guard.mjs 同步按 LOCALES 复制 404 产物，两者都不需要改；只需给 _headers 与 _redirects 各补 2 条对应前缀的规则。

译文按内容形态分两类：参数型内容写在条目的 locales 键下，正文型按 zh/ 子目录分文件。整块缺译或必填字段缺失直接判错，不做「英文正文 + 中文标题」的假中文页。

SECTION 06

风险清单

按「发生概率 × 影响面」排，前四条是本项目最容易踩的。

风险等级缓解措施
误配通配 200 rewrite，任意路径返回首页副本高_redirects 禁止 SPA fallback；部署后第 ① 条 curl 验真 404
404 产物被边缘缓存固化或被直访收录高_headers 设 no-store、_redirects 挡直访、页面自带 noindex
新增语言后该语言路径的 404 变成英文页中构建守卫按 LOCALES 复制 <prefix>/404.html；新增语言只需给两份规则文件各补 2 条
导出文件含客户信息被提交进仓库高备份另存受控位置；仓库内只保留建表语句与命令示例，不存真实数据
凭证泄露高本地 wrangler login，CI 用环境变量；.env 与 .wrangler/ 已忽略
占位 database_id 忘了回填中写进上线前检查表，d1 create 后立即回填 wrangler.toml
占位域名跟着产物上线中CI=true 或 REQUIRE_REAL_DOMAIN=1 时构建直接失败
「上线即有线索库」的误解中运维手册写明表单走 mailto，数据由 Wrangler 按需录入
Git 集成构建为浅克隆，逐页 lastmod 被静默省略中Pages 构建配置使用完整 git 历史；部署前抽查 sitemap 的 lastmod
构建时长随页面数增长低监控单次构建时长；内容随代码同仓，静态产物可预生成
不要开 SPA fallback；不要给 404 配长缓存；不要提交含客户数据的 .sql。这三条是本方案里为数不多「配错了不会立刻报错、但会持续损害 SEO 或合规」的地方。

上线前必须过的检查

十项状态验证，逐条打勾再发生产。占位资产与部署配置的替换清单另见 deploy/cloudflare/README.md 第 7 节（唯一权威）；本节只验结果，不重复列配置。

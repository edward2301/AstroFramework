# 开发框架设计

> 项目：B2B 工业品出口站
> 技术栈：Astro 7.x（见 `package.json`）· TypeScript strict · Node 以 `.nvmrc` 为准

---

## 1. 整体架构分层

Astro 的运行模型是「内容 → 构建 → 静态产物」，没有运行期服务端。分层必须匹配这一模型，不能照搬 MVC 或前后端分离那套。

```
┌──────────────────────────────────────────────┐
│  L6  构建层    astro.config · 校验脚本 · Pages 部署 │
├──────────────────────────────────────────────┤
│  L5  页面层    src/pages        路由与组装       │
├──────────────────────────────────────────────┤
│  L4  布局层    src/layouts      页面骨架         │
├──────────────────────────────────────────────┤
│  L3  组件层    src/components   展示与交互       │
├──────────────────────────────────────────────┤
│  L2  数据层    src/lib          仓储与领域逻辑    │
├──────────────────────────────────────────────┤
│  L1  内容层    src/content      数据源与 schema  │
└──────────────────────────────────────────────┘
               横切：SEO · 样式 · 资源
```

### 1.1 各层职责

| 层 | 职责 | 不做什么 |
|---|---|---|
| L1 内容层 | 定义集合、schema、数据文件 | 不写展示逻辑，不做数据加工 |
| L2 数据层 | 仓储（`lib/content`，集合查询/排序/草稿过滤/关联解析）· 载荷装配（`lib/pages`）· SEO（`lib/seo`）· 导航派生（`lib/nav`） | 不产出 HTML，不依赖组件 |
| L3 组件层 | 渲染 UI，接收 props，无副作用 | **不直接读取内容集合** |
| L4 布局层 | 页面骨架（头部、页脚、主区域），把派生好的导航渲染出来 | 不承载业务数据查询 |
| L5 页面层 | 路由枚举与分派（`[...slug].astro`）；静态页数据来自 `data/pages/entries` | 不写可复用的展示逻辑 |
| L6 构建层 | 配置、集成、构建期校验 | 不参与页面渲染 |

### 1.2 核心设计原则

**页面不直接调用 `getCollection`，一律经 `src/lib/content`。**

这是整个框架最重要的一条约束。理由：

- schema 变更时，只需改仓储层，不必全站搜索替换
- 关联解析（替代型号、应用推荐）集中一处，避免各页面各写一遍
- 草稿过滤、排序规则、可见性判断统一，不会漏掉某个页面
- 将来若切换数据源（Git → CMS），只需替换仓储层实现，页面无感知

## 2. 核心模块划分

| 模块 | 位置 | 职责 | 关键产出 |
|---|---|---|---|
| 内容定义 | `src/content.config.ts` | 内容集合的 loader 与 schema | 类型安全的集合查询 |
| 内容数据 | `src/content/*` | 型号、品类、应用、案例、指南、问答、资料 | 内容源文件 |
| 站点数据 | `src/data/*` | 站名与后缀、组织实体、页脚分区顺序等非集合常量 | 常量与配置 |
| 仓储层 | `src/lib/content/*` | 集合查询、排序、过滤、关联解析 | 语义化查询函数 |
| SEO 引擎 | `src/lib/seo/*` | 元标签生成、结构化数据构造、面包屑 | 每页唯一的 SEO 载荷 |
| 页面条目 | `src/data/pages/*` | 一页一文件：path、SEO、正文、导航落点 | 静态页的唯一登记处 |
| 导航派生 | `src/lib/nav.ts` | 读条目 nav 字段，产出主导航与页脚。同一 URL 只占一个位置——与页眉 CTA 同目标的页面（如询价页）不设 `nav.main` | 全站导航结构 |
| 路由常量 | `src/data/routes.ts` | 从条目 path 派生一级路径与详情拼接 | 全站链接与路由的唯一来源 |
| 载荷装配 | `src/lib/pages/*` | `static.ts` 按版式装静态页，`render.ts` 按集合装内容页 | 每页唯一的渲染载荷 |
| 布局 | `src/layouts/*` | 当前只有 `BaseLayout`（唯一骨架） | 页面外壳 |
| 布局组件 | `src/components/layout/*` | 头部、页脚、PageHeader、SectionTitle、CtaBand、FeatureRow | 骨架组件 |
| 卡片组件 | `src/components/cards/*` | CategoryCard（品类卡）、ModelTile（次级磁贴） | 可复用的内容卡，交互规则内聚 |
| 应用选型卡 | `src/components/catalog/ApplicationCard` | ApplicationCard（工况名+条件+型号数，无图片） | 首页「按应用选型」专用 |
| 目录组件 | `src/components/catalog/*` | ComparisonTable（品类对比表）、PurchaseFacts（采购信息 4-up） | 参数唯一出处的数据表 |
| 页面主体 | `src/components/pages/*` | 各类版式的 Body 组件（HomeBody · ModelBody …） | 只渲染，不取数 |
| SEO 组件 | `src/components/seo/*` | 输出 meta、JSON-LD | 无渲染的头部注入 |
| 构建校验 | `scripts/*` | 内容体检、链接检查 | 构建失败的拦截 |

> `components/ui` / `product` / `content`、`layouts/ProductLayout` 等目录
> 一律不预先建立空目录。

### 3.1 命名约定

| 对象 | 规则 | 示例 |
|---|---|---|
| 集合目录 | 复数、小写、连字符 | `models/` `cases/` |
| 内容文件 | 与 URL slug 一致 | `a1.json` → `/products/a1/`；`guides/install-checklist.md` → `/resources/guides/install-checklist/` |
| Astro 组件 | PascalCase | `ApplicationCard.astro` |
| 布局 | 后缀 `Layout` | `BaseLayout.astro`（当前唯一布局） |
| 工具模块 | 小写、按域分组 | `lib/content/models.ts` |
| 查询函数 | 动词开头、语义化 | `getModelsByCategory()` |

### 3.2 目录范围

只为实际使用的模块建目录，不预留空目录与占位组件。`BaseLayout` 提供全站骨架（头部、页脚、SEO 出口），业务结构留在页面内；品类页与型号页除面包屑与页面级样式外没有共用结构，不需要第二层布局。

`dist/404.html` 与 `dist/zh/404.html` 各一份、`noindex`（后者由构建守卫从 `dist/zh/404/index.html` 复制，供 Pages 按前缀就近查找）。资料下载由 `static.ts` 的 `sectionContent()` 读 `downloads` 集合渲染列表，列表项直达 `file` 字段。

未实现的路径登记在 `scripts/check-links.mjs` 的 `PENDING_ROUTES` 中，构建只警告不阻断；未登记的断链会让构建失败。

## 4. 模块依赖关系

### 4.1 依赖方向

```
src/pages ──▶ src/layouts ──▶ src/components ──▶ src/lib/utils
    │              │               │
    │              ▼               ▼
    └────▶ src/lib/seo              src/data/  (pages/entries · navigation · site · organization)
    │              ▲
    └────▶ src/lib/pages ──▶ src/lib/content ──▶ src/content/  (L1)
                 │
                 └──▶ src/lib/nav（读 src/data/pages 的 nav 字段）
```

`src/pages` 依赖 `src/lib/*` 时经 `src/lib/pages/{static,render}.ts` 统一进 `src/lib/content` 与 `src/lib/seo`：
`static.ts` 按版式装静态页（数据来自 `src/data/pages/entries/`），`render.ts` 按集合装内容页；
导航由 `src/lib/nav.ts` 从页面条目派生，布局层只把它渲染出来。
路由文件 `[...slug].astro` 本身只做路径分发，不直接写装配逻辑。

### 4.2 允许与禁止

| 模块 | 可依赖 | **禁止依赖** |
|---|---|---|
| `pages` | `layouts` `lib/*` `data/*` | 不得被任何模块依赖 |
| `layouts` | `components/*` `lib/seo` `data/*`、**`lib/content/site`** | 不得调用 `getSiteNav()` 以外的任何内容查询 |
| `components` | `lib/utils` `data/*` | **不得依赖 `lib/content`**（数据一律由 props 传入） |
| `lib/content` | `content.config` `lib/utils` | 不得依赖任何组件或布局 |
| `lib/seo` | `data/site` `data/organization` `data/navigation` `lib/utils` | 不得依赖 `lib/content` |
| `lib/pages` | `lib/content` `lib/seo` `data/pages` `data/navigation` `i18n/*` | 不写展示标记 |
| `lib/nav` | `data/pages` `data/navigation` `i18n/*` | 不硬编码任何链接 |
| `data` | `i18n`（仅 type）、同目录文件 | 不得依赖 `lib/*` 与任何组件 |

> **布局层的唯一例外**：`BaseLayout` 需要品类与应用方向来渲染导航与页脚，这类数据属于站点结构而非页面业务数据。若逐页取数再透传，每个页面都会背上一段与自身无关的查询。因此 `src/lib/content/site.ts` 单独暴露 `getSiteNav()`，布局层只允许调用这一个函数。

> **组件的类型例外**：`Breadcrumb.astro` 从 `src/lib/seo/breadcrumb` 导入 `Crumb` 类型，属 type-only 依赖，不产生运行期耦合。组件不得从 `src/lib/seo` 导入任何函数或值。

### 4.3 三条硬性规则

**规则一：组件不取数。**
`src/components/**` 内不出现 `getCollection` / `getEntry`。所有数据由页面或布局通过 props 传入。这样组件可在任意上下文复用，也便于单独调试。

**规则二：页面不手写 SEO 标签，但可以提供文案。**

页面里不出现 `<title>`、`<meta name="description">`、`<script type="application/ld+json">`。全部经 `BaseLayout` → `<SEO>` 与 `<JsonLd>` 输出。

文案的来源分两种：内容页取该条内容自带的 `seoTitle` / `seoDescription`；栏目页与首页在页面内声明，但**必须经 `buildMeta()` 处理**——它负责补品牌后缀并把长度不合规变成构建失败。页面直接写标签则绕过了这道关口。

**规则三：关联不在展示层解析。**
正向关联（型号的 `replacement` / `applications` / `relatedCases`）由 `src/lib/content/models.ts` 的 `getModelDetail()` 用 `getEntries()` 解析成完整对象；`src/lib/content/relations.ts` 只负责**反向关联**（某型号被哪些 `applications.recommended` / `cases.config` 引用），用一次遍历建 `Map<modelId, BacklinkIndex>`，由 `getModelBacklinks()` 查询。两者都在仓储层完成，模板里不做二次查询。

## 5. 内容层设计

### 5.1 集合定义

配置文件为 `src/content.config.ts`（非 `src/content/config.ts`）。

> 以下只写设计不变量与字段归属；字段全集、默认值、枚举、长度限制以 `src/content.config.ts` 为准，必填译文以 `scripts/validate-content.mjs` 的 `REQUIRED_TRANSLATION` 为准。

| 集合 | 存储 | 关键字段 | 译文形态 |
|---|---|---|---|
| models | JSON | code、category、status、replacement、keyParams、specGroups、image、applications、relatedCases | `locales.<lang>` |
| categories | JSON | intro、comparisonParams、selectionPoints、purchaseInfo、color、order | `locales.<lang>` |
| applications | JSON | condition、criteria、recommended、cautions | `locales.<lang>` |
| cases | JSON | background、requirements、selection、config、results、date | `locales.<lang>` |
| guides | Markdown | title、tldr、updated、relatedModels、relatedApplications | 同 slug 的 `zh/<slug>.md` |
| faqs | Markdown | question、cluster、relatedModels、relatedFaqs | 同 slug 的 `zh/<slug>.md` |
| downloads | JSON | docType、version、updated、model?、gated、file | 仅可选 `locales.<lang>.title` |

**跨集合不变量：**

- 所有集合都有 `draft`，默认 `false`；草稿不生成路由、不进列表、不参与关联解析，已发布条目引用草稿会在校验时报错。
- `keyParams` 固定 5 项；`specGroups` 至少 1 组、每组至少 1 行；品类 `intro` 源语言 ≥300 字、译文 ≥150 字；`comparisonParams` 5–7 项；应用 `recommended` 2–5 个。精确约束以 `content.config.ts` 为准。
- `comparisonParams` 与同语言型号的 `keyParams.k` 必须同名。品类写 `IP Rating`、型号写 `Protection` 时，构建不报错，对比表对应单元格渲染 `—`；校验在 `scripts/validate-content.mjs` §1.1（逐语言）与 §4（默认语言）。
- 除 `downloads` 外，每条内容都自带 `seoTitle` / `seoDescription`。`seoTitle` 只写本体，品牌后缀由 `src/lib/seo/branding.ts` 单点拼接；`seoDescription` 独立撰写，不复制其他条目。
- `downloads` 不单独成页；列表出现在 `/resources/downloads/`，`certificate` 类型同时出现在 `/certifications/`（`src/lib/pages/static.ts` 的 `sectionContent()`）。

**两条必须成对理解的约束：**

- **对比表列与参数键同名。** 渲染按 `k` 匹配，不匹配时对应单元格是 `—`，构建不报错；这是本仓最容易漏检的内容错误，必须靠脚本 §1.1/§4 和人工抽查兜住。
- **SEO 标题/描述由编辑撰写。** 不做模板拼接：大量型号会产出大量结构雷同的标题，长型号还会被截断。`src/lib/seo/meta.ts` 只补后缀、校验长度与唯一性，不创作文案。

### 5.2 存储格式选择

| 内容 | 格式 | 理由 |
|---|---|---|
| 型号、品类、应用、案例、资料 | JSON | 字段密集、以结构化数据为主，正文叙述短 |
| 指南、问答 | Markdown | 以长文正文为主，需要富文本与排版 |

同一条内容不混用两种格式。型号页的叙述性内容放在 `specGroups` 之外的字段里，不进 Markdown。

### 5.3 仓储层

实现见 `src/lib/content/models.ts`、`src/lib/pages/render.ts` 与 `src/pages/[...slug].astro`。本节只列必须成立的行为。

**仓储层不变量：**

- 型号列表查询排除 `draft`；默认排除停产，只有显式要求时才包含；结果按 `code` 排序。
- 详情查询：条目不存在或为草稿时返回 `null`；`replacement` / `applications` / `relatedCases` 一次解析完成，解析结果再过滤一遍草稿。
- 正向关联在仓储层完成，反向关联在 `relations.ts` 完成；模板不做二次查询。

**页面调用不变量：**

- 内容页只有一个分发器；`getStaticPaths()` 遍历 `LOCALES` ×（页面条目 + 各集合），入口只有 `loadPage()`。
- `loadPage()` 收到 `kind: 'static'` 转 `static.ts` 按版式装配，其余 kind 由 `render.ts` 按集合装配。
- 页面不出现 `getCollection`；取不到条目时抛错，不用 `Astro.redirect('/404')`——静态模式会生成跳转页，不是 404。

### 5.4 多语言

**路由结构：默认语言不带前缀，中文带 `/zh`。**

```
/products/a1/       英文
/zh/products/a1/    中文
```

不采用 `/en/` + `/zh/` 双前缀：英文站是面向海外买家的主站，根路径即英文可以少一层跳转，也不会让既有外链与收录历史失效。

**内容 slug 两种语言共用。** 翻译 slug 会产出两套 URL 体系，收益仅是外观，代价是重定向表、内链重写、以及 slug 一致性校验要按语言各写一套。

**四层文案，各有归属。** 完整分层表（哪层放哪、由谁维护）见 `docs/上手指南.md` §5.2，此处只讲为什么分开：

分开的理由很实际：运营改一句产品描述，不该需要动代码；开发改一个按钮文案，也不该去翻 300 个 JSON。

**两种翻译结构，按内容形态分工。** 这一点必须写死，否则两种存法会互相渗透：

| 内容形态 | 集合 | 翻译存放方式 | 理由 |
|---|---|---|---|
| 参数型 | `models` `categories` `applications` `cases` | 同一文件内嵌 `locales[语言]` 对象 | 参数数值必须唯一。两套语言记录各自维护数值，迟早出现「英文 1.6MPa、中文 1.5MPa」这种对照不上、却都能通过校验的情况 |
| 正文型 | `guides` `faqs` | 一个语言一个文件：`foo.md` 与 `zh/foo.md` | 正文是页面主体，要和结构化字段一起被当作独立篇章收录。正文塞进 frontmatter 既不可读，也没法做语法高亮与相对图片引用 |

正文型的语言由**目录前缀**表达（`routing.ts` 的 `localeOfEntryId`），schema 无 `locale` 字段——少一个字段就少一处写错的机会。缺某个语言的文件时，**该语言页面根本不生成**，而不是拿源语言正文凑一个页面出来。

两种结构共用的约束：标题与描述必须各语言独立撰写，不得互译照抄——同一句话翻两遍的 `title` 会被判重复，跨语言查重由构建脚本统一拦截。

**译文：语言块必填，必填字段不可分批。** 参数型集合的 `locales` 里只要出现了某一语言，`REQUIRED_TRANSLATION` 列出的必填字段就必须齐全；没有该语言块则构建失败。`dimensions`、`interface` 等补充字段不在必填表内，缺失时直接回落源语言，**不报错也不告警**。正文型集合由「配对校验」把关：每个 slug 必须在每个语言下都有文件，缺一个即构建失败，报错直接给出应新建的路径。理由见下一条。

**视图函数按语言键查表，不判断具体语言。** `categoryView(entry, locale)` 内部只做 `entry.data.locales?.[locale]`，无论现有两种语言还是将来五种，都不存在「漏写某个语言的判断分支」。按具体语言写判断分支时，新语言会**静默**渲染源语言内容——构建通过、链接正确、页面全英文，比链接跳错更难发现。

**缺译是错误，不是告警。** 缺少某一语言块会直接中止构建，报错写明缺哪个条目、缺哪种语言。想「先出英文后补译文」的正确做法是不发布该语言的这个页面，而不是带着源语言内容上线。

**页面只传语言无关路径。** 页面写 `path="/products/"`，布局据此推导 canonical、hreflang、`<html lang>`、`og:locale`。页面自己拼前缀会导致三种来源的地址不一致，而这在产物里看不出异常。

**为什么中英文页面共用一套 body 组件：** 若各写一份，改一处 UI 要改两处，第二处迟早漏。单路由分发器 + `src/lib/pages` 的装配函数只做「取数 → 拼 SEO → 传参」，渲染全在 `src/components/pages/*Body.astro`。

`content.config.ts` 导出各集合的 `locales` 子 schema（`modelLocales` / `categoryLocales` / `applicationLocales` / `caseLocales`），`localize.ts` 的 `translationOf()` 用 `z.output<S>` 派生译文类型——schema 改字段时视图的编译会跟着变，不会出现两份手写副本漂移。

404 每种语言各一份，产出与就近查找机制见 `deploy/cloudflare/README.md` §6。
页脚与询价页的公司地址、`Organization` 描述来自 `src/data/organization.ts`：
`locales.zh` 提供中文 `description` 与 `address`，`organizationFor(locale)` 按语言返回；
`name` / `legalName` / `contactPoint` / `sameAs` 不翻译。

## 6. SEO 层设计

SEO 是横切关注点，不归属某一层，但必须有唯一出口。

### 6.1 单一入口

实现见 `src/components/seo/SEO.astro` 与 `src/layouts/BaseLayout.astro`。组件只输出，不校验；长度与唯一性在 `buildMeta()` 与校验脚本中完成。

| 输入/输出 | 规则 |
|---|---|
| `title` | 必须是已含品牌后缀的完整标题；组件不再拼接 |
| `description` | 原样输出 `<meta name="description">` |
| `canonical` | 相对路径，已含语言前缀；经 `absoluteUrl()` 转绝对地址 |
| `image` | 缺省用 `SITE.ogImage`；经 `absoluteUrl()` |
| `noindex` | 为真时不输出 canonical、`og:url`、hreflang、JSON-LD，只输出 `noindex, follow` |
| `alternates` | 输出 hreflang 与 `og:locale:alternate`；`BaseLayout` 在 `noindex` 时清空 |
| `ogType` / `locale` | 输出 Open Graph 类型与 `LOCALE_META` 对应值 |

**三个设计取舍：**

- 绝对地址只走 `absoluteUrl()`，不用 `new URL(x, Astro.site)`。
- 组件只管输出，不校验；校验在 `buildMeta()` 与脚本。
- `title` 已含后缀，组件不再拼；后缀只由 `branding.ts` 拼。

`noindex` 页（404）不输出 canonical、`og:url`、hreflang 与 JSON-LD；`BaseLayout` 在 `noindex` 时把 `alternates` 置空。

### 6.2 生成与校验分离

校验分两层，责任人不同：

| 层 | 位置 | 管什么 | 失败方式 |
|---|---|---|---|
| 页面级 | `src/lib/seo/meta.ts` 的 `buildMeta()` | 标题后缀补全、标题与描述的长度 | **直接抛错**，中断构建 |
| 内容级 | `scripts/validate-content.mjs` | 标题全站唯一、引用完整性、编码与文件名一致、对比表列覆盖 | 退出码 1，中断构建 |

**页面级为什么要抛错而不是返回 issues：** 返回数组、由调用方决定要不要处理，这种 API 在真实项目里一定会被忽略（只打一行日志）。长度不合规的页面不应该进入产物，因此校验即失败点，没有「先放过」的选项。

**内容级为什么必须独立成脚本：** 它依赖跨条目的关系——同一标题是否在别的文件里出现过、`replacement` 指向的型号是否存在、品类的对比列是否被每个型号覆盖。zod 只能校验单个条目，跨条目规则写不进 schema。

两层都在构建期执行。Astro 的页面渲染发生在构建时，运行期没有断言机会；把关卡放在产物生成之前，是唯一能保证「不合格内容进不了产物」的位置。

## 7. 技术约束

### 7.1 强制项

| # | 约束 | 检查方式 |
|---|---|---|
| 1 | 所有集合必须定义 schema，不得使用 `z.any()` | 代码评审 |
| 2 | 组件内不得出现 `getCollection` / `getEntry` | 代码评审 |
| 3 | 页面不手写 `<title>` / `<meta>` / JSON-LD | 结构保证：页面不直接写 `<head>`，只有 `BaseLayout` 输出 |
| 4 | 宽度在 `SEO_LIMITS` 内（**按显示宽度，全角计 2**） | 页面级 `buildMeta` 抛错 + 脚本校验 |
| 5 | 标题全站唯一 | 脚本校验 |
| 6 | 图片放 `public/images/…`，用裸 `<img>`，不做构建期处理（见 §7.5） | 脚本校验 `width`/`height`/`alt`/`loading` 与文件存在性 |
| 7 | 每页唯一 `<h1>` | 代码评审 |
| 8 | 每个内容页必须有可见面包屑 | 页面同时输出 `Breadcrumb` 组件与 `breadcrumbSchema`，共用同一 `crumbs` 数组 |
| 9 | 不存在的路由返回 404 | 静态产物不含多余路径，`public/_redirects` 不得配 SPA fallback；按 `deploy/cloudflare/README.md` §5 的 curl 清单实测 |

**关于第 4 项：** 区间来自站点元标签规范；下限不是排版偏好，而是信息完整度的代理指标——低于下限通常意味着少了量程、精度、防护等级或认证中的一项。占位品牌名较短时标题容易落到下限以下，此时应补一项真实参数，而不是放宽下限。具体数值读 `SEO_LIMITS`。

### 7.2 TypeScript

- 继承 `astro/tsconfigs/strict`（已配置）
- 禁止 `any`；不确定类型用 `unknown` 并收窄
- 集合查询结果不得断言为非空。动态路由用 `getStaticPaths()` 生成全部路径，页面内取不到条目时**抛错中断构建**，不用 `Astro.redirect('/404')`（静态模式下它产出跳转页，不是 404）

### 7.3 运行环境

Node 版本由 `.nvmrc` / `.node-version` 锁定，`package.json` 的 `engines` 约束 `node` 与 `npm`；三处必须一致。Astro 7 自身在 `node_modules/astro/package.json` 的 `engines` 里声明最低 Node 版本，低于它 `astro build` 会直接拒绝执行。

版本不对是环境问题，不是代码问题：先 `nvm use`（或 fnm/volta）切到 `.nvmrc` 的版本再构建，不要据此改代码。

仅当版本管理器不可用时临时指定（PowerShell）：

```powershell
$env:Path = "C:\Program Files\nodejs;$env:Path"
```

Cloudflare Pages 构建环境必须显式声明 Node 版本（读取 `.nvmrc`，或设置 `NODE_VERSION` 与 `.nvmrc` 一致），不得依赖构建机默认值；CI 环境同理。

### 7.4 禁止事项

- 不使用双套 DOM 实现响应式（桌面表格 + 移动卡片）
- 不在客户端引入框架运行时，除非确有交互需求
- **客户端交互脚本共两段，无框架、只处理交互**：
  1. 页眉滚动状态（`Header.astro` 的 `is:inline` 脚本，仅首页 overlay 变体渲染）：滚动超过阈值后把透明浮层切换成白底黑字，
     否则白字会压在白底内容上。
  2. 询价表单（`src/components/pages/QuoteBody.astro` 的普通 `<script>`）：必填项与邮箱格式校验、防重复提交、
     按 `data-mailto` 拼 mailto 并显示回落链接；不提交到服务端。
  `JsonLd.astro` 里的 `<script type="application/ld+json" is:inline>` 是结构化数据，不属于交互脚本。
  新增客户端交互前先问：能不能用纯 CSS（scroll-snap / details / :hover）达成
- 不让构建处理图片（转码、生成多尺寸）：那是运营上传前的事，见 §7.5
- 不为「将来可能用到」预留空目录与空模块

### 7.5 图片与静态资源

**图片是运营资产，不经过构建处理。** 构建只做一件事：把 `public/` 原样复制进 `dist/`。

```
public/images/models/a1.png          ← 运营按编码放图，一图一名
src/content/models/a1.json           "image": "/images/models/a1.png"
src/components/pages/ModelBody.astro         <img src={image} …>
```

**为什么不进构建管线：**图片本就该在上传前压好。一旦让构建去转 WebP、生成多尺寸，构建时间就会随图片数量线性增长，而且每次构建都重算一遍——可绝大多数构建里图片根本没变，重算是纯浪费。

**运营需要遵守的四条：**

| 项 | 要求 |
|---|---|
| 路径 | `public/images/models/<型号编码>.png`（或 `.webp`），一图一名；多图加序号后缀（`a1-2.png`） |
| 尺寸 | 黄金比 1.618:1，800×494（页面按 1.618 预留位置，比例不同只会轻微跳动） |
| 体积 | ≤ 100 KB，优先 WebP |
| 替换 | 同名覆盖即可，不改代码、不动 JSON |

**程序这边保证的四条：**

| 项 | 做法 |
|---|---|
| 宽高 | `<img>` 手写 `width`/`height`（黄金比 1.618），防布局跳动 |
| alt | 型号 + 产品名，跟随译文 |
| 首屏加载 | `loading="eager"` + `fetchpriority="high"` + `decoding="async"` |
| 路径写错 | `validate` 检查 `public/` 下文件是否存在；`image` 可缺省，填写后文件不存在才判错（`ModelBody` 为条件渲染，缺图不输出 `<img>`）；`datasheet` / `downloads.file` 缺失为告警、页面不输出对应链接 |

**已知取舍：**只有一档图，手机和桌面下同一张。图已压到 ≤100 KB 时，多下几十 KB 比维护三套尺寸便宜。要做响应式就得回到"构建期生成多尺寸"，那是另一个方向。

型号页主图的 `<img>` 写法见 `src/components/pages/ModelBody.astro`；必须带 `width`、`height`、`alt`、`loading`，首屏主图再加 `fetchpriority="high"` 与 `decoding="async"`。

**校验（`scripts/validate-content.mjs`）**

| 规则 | 级别 |
|---|---|
| `image` 填写后，指向的文件在 `public/` 下存在 | 错误（填写即输出 `<img>`，缺图即破图；`image` 缺省不判错） |
| 任何 `<img>` 必须带 `width` / `height` / `alt` / `loading` | 错误 |

扫描前会屏蔽注释（`<!-- -->`、`/* */`、独占一行的 `//`），避免注释里提到 `<img>` 时误报。

**与 SEO 的对接：**`Product.image` 与 `og:image` / `twitter:image` 自动取这张图的绝对 URL（`https://example.com/images/...`）；没有图的页面回落到 `SITE.ogImage`。图片已在 HTML 里，常规抓取能发现，无需图片 sitemap。

## 8. 配置规范

### 8.1 内容写入路径

**决策：纯文件管理，不引入 CMS。**

- 型号、品类、应用、案例、资料：JSON 文件
- 指南、问答：Markdown 文件
- 全部内容随代码同仓；发布用 `npm run deploy`（构建后经 Wrangler 上传到 Cloudflare Pages），也可在 Pages 配置 Git 集成自动构建，两者跑同一个 `npm run build`

选择理由：

1. 内容由运营逐个添加，起始量级很小，不存在批量导入需求
2. 文件形式天然具备版本追溯与回滚能力，无需额外投入
3. 数据层已隔离在 `src/lib/content`，若将来确需可视化后台，只需替换这一层，页面与组件不受影响

**格式分流的依据：** 型号类内容的本质是结构化参数，而非叙述文本。用 JSON 可获得编辑器的字段提示与类型校验；用 Markdown 存多层嵌套的参数数组，缩进与转义极易出错。指南与问答以长文为主，Markdown 更合适。

同一类内容不混用两种格式。型号页的叙述性内容放在 JSON 字段中，不进 Markdown。

### 8.2 样式方案

| 方案 | 优势 | 劣势 |
|---|---|---|
| Tailwind | 与 Astro 集成好，设计一致性易保证 | 需构建依赖，模板类名较长 |
| 原生 CSS + 变量 | 零依赖，产物最小 | 需自行建立设计系统 |
| CSS Modules | 作用域隔离 | 复用设计变量较繁琐 |

**原生 CSS + 设计变量**（`src/styles/tokens.css` + `global.css`）。版式由 `contract.ts` 的 `PageDef` 联合与内容 `PageInput` kind 决定，Body 组件清单见 `src/components/pages/`；无构建依赖也更契合性能目标。若团队已熟悉 Tailwind，可整体替换，不影响分层结构。

**令牌分组**（具体值以 `tokens.css` 为唯一来源，本表只写角色与规则）：

| 分组 | 令牌 | 角色 |
|---|---|---|
| 中性面 | `--color-bg` / `-surface` / `-subtle` / `-sunken` | 页面底、卡片、分区与表头、次级面板 |
| 文字 | `--color-text` / `-ink` / `-muted` | 正文、标题与深色带、次要文字 |
| 边框 | `--color-border` / `-strong` / `-soft` / `-brand` | 分隔线、输入框、弱分隔、品牌着色边 |
| 动作 | `--color-action`（填充主按钮）/ `-link`（文字链接）/ `-focus` | 信号蓝只用于这三处 |
| 数据 | `--color-data` / `-data-soft` | 指标线、对比表强调、采购信息块（石墨，不再用铜色装饰） |
| 深色带 | `--color-on-dark` / `-muted` / `-active` | hero、页脚、CtaBand 内文字 |
| 排版 | `--fs-*` / `--lh-*` / `--ls-*` / `--measure*` | 流式字号（clamp）、行高、字距、可读行宽 |
| 布局 | `--container`（1920）/ `--container-narrow`（1280）/ `--gutter`（24–40）/ `--space-1..10` / `--header-h` | 全宽流式容器、详情页阅读宽度、栅格、节奏 |
| 形状/动效 | `--radius-*`（0）/ `--shadow-*`（none）/ `--duration-1..3` / `--ease` | 直角、无阴影，层级靠 1px 细线；120/180/280ms |
| z-index | `--z-sticky / -header / -dropdown / -mobile-nav / -skip` | 层叠顺序 |

**组件契约**（实现在 `global.css` 与 `src/components/layout/`）：

- 按钮：全站唯一一套 `.btn`（44px 高、直角）+ 变体 `--primary / --secondary / --ghost / --on-dark` 与尺寸 `--sm / --lg`；局部按钮样式一律删除，每个视口区域只允许一个填充主按钮。
- 卡片：统一 `.card`（直角、无默认抬升）；徽标 `.badge`、chip `.chip` 同为直角；型号编码统一 `.mono`。
- 详情页排版片段（`global.css`「详情页复用片段」）：`.stack`（正文纵向节奏）、`.lede`（日期行 + 导语）、`.intro`（导语段）、`.detail-meta`（日期行，与 `.mono` 连用）、`.aside-title`（侧栏分组标题）、`.points`（mono 序号 + 细线行列表，`--muted` 变体）。应用/案例/指南/问答四个 Body 与品类页选型要点共用，类名是组件间契约，改名需同步全部使用方。
- 列表工具（`global.css`「共享列表工具」）：`.grid-list`（列表型卡片网格 reset，与 `tile-grid / card-grid / app-grid / items / metrics` 成对使用）、`.chip-list`（chip 横排 reset，与 `cert-chips / sibling-chips` 成对使用）；列宽、间距等专有规则仍留在各组件作用域。
- 表格：`.data-table`（表头浅底、小号大写）、`.spec-table`（键值规格）、外层 `.table-scroll`（表内横滚，页面不溢出）。
- PageHeader：石墨深色带（`--color-ink` 底 + `--color-on-dark*` 文字，与首页 hero 同一色系），置于 `.section` 之外（内部自带 container），`width: 'wide' | 'narrow'`（1920 / 1280），`meta` 数据行 + `actions` slot；是全站唯一 h1。紧跟其后的首个 `.section` 由全局规则收紧上边距至 space-5，且首个板块标题（`.section-title:first-child`）不再画分隔线——页头深色带本身已完成分隔，两条细线夹空白会像渲染残留。
- 详情页：应用/案例/指南/问答使用 `DetailLayout`（760px 正文 + 320px sticky 相关栏），型号链接统一走 `ModelLinkList`；≤1024 堆叠。
- SectionTitle：h2 + 细线 + 可选右侧链接，替代旧的全局 h2 竖条（已删除）。
- CtaBand：石墨 full-bleed 转化横条，内部自带 container。
- 断点：480 / 768 / 1024 / 1280 / 1440；header 与移动导航在 1024 折叠；卡片/规格网格优先 `auto-fit|auto-fill minmax(min(100%, Npx), 1fr)`，不新增断点。同一断点在每个组件的 style 块里只允许一个 `@media` 块——新规则并入既有块，并置于对应 base 规则之后（media 不提升优先级，覆盖靠源顺序）。
- 动效：全局 `prefers-reduced-motion` 关闭平滑滚动、卡片抬升与图片 zoom；常规态也不做抬升/缩放。
- 移动端触摸目标：按钮、筛选 pill、输入框、卡片入口、表格内链接、页脚栏目链接均 ≥44px；面包屑与栏目标题链接属行内文本例外，不强制。

### 8.3 astro.config.mjs

配置全文以 `astro.config.mjs` 为唯一来源。按 §3「不写需要人肉维护的第二份真相」的约定，
本节只写**约束与设计意图**，不复制代码。

配置要点：

- `site` 是域名的唯一来源（`src/lib/seo/meta.ts` 通过 `import.meta.env.SITE` 读取），必须填真实域名；占位域名在 CI 下会让构建失败。
- `trailingSlash: 'ignore'`：「末尾统一带斜杠」由链接层（`localizePath`）保证，canonical、内链与 sitemap 全部以 `/` 结尾。匹配策略不用 `'always'`——那会让 astro dev 在路由前拦截无尾斜杠请求（合法页直接 404、未知页弹 Astro 品牌提示页，中间件拦不到）；dev 的 308 归一由 `astro.config.mjs` 的 `devTrailingSlash` 集成（`astro:server:setup` unshift 到 connect 栈顶）完成，与 Pages 线上行为一致
- `build.format: 'directory'` 生成目录式产物，便于 Cloudflare Pages 按路径前缀就近查找 `404.html`
- `i18n` 全部取自 `src/i18n/routing.ts`，无手写副本；`sitemap.i18n.locales` 用 `LOCALE_META` 的 `htmlLang`（`en` / `zh-CN`）
- `sitemap.filter` 排除 404，`serialize` 用 `src/lib/seo/lastmod.ts` 写逐页 `lastmod` 并补 `x-default`；`contentGuard()` 把两个校验脚本挂进构建生命周期
- `public/_redirects` 不配置 SPA fallback（不写通配 200 rewrite），避免任意路径返回 200
- `process.env.CI === 'true'` 或 `process.env.REQUIRE_REAL_DOMAIN === '1'` 时，`site` 仍为 `example.com` 会直接让构建失败
- `base` 保持默认 `/`：当前方案使用 Pages 自定义域的根路径。框架本身支持子路径（`absoluteUrl()` 与 `robots.txt` 按 `BASE_URL` 拼接），但本方案不使用

### 8.4 构建脚本

脚本定义以 `package.json` 的 `scripts` 为唯一来源，此处不复制。`deploy` = `npm run build` + `wrangler pages deploy`；完整命令与环境配置见 `deploy/cloudflare/README.md`。

质量门与执行时机见 `docs/上手指南.md` §2.2。`scripts/build-guard.mjs` 挂在 `astro:build:start` 与 `astro:build:done`：前者内容体检与文档对账，后者复制分语言 404、把型号旧路径 301 写入 `dist/_redirects` 并检查内链；因此直接 `astro build` 也不能绕过校验，产出的 `dist/` 可直接上传。云端构建需要完整 git 历史（逐页 `lastmod` 依赖 `git log`）。

校验脚本的职责分层：

| 层 | 脚本/入口 | 管什么 | 失败方式 |
|---|---|---|---|
| 内容级 | `validate-content.mjs` | SEO 宽度/唯一性、编码与文件名、引用、对比表列、缺译、路径/导航、图片路径与 `<img>` 属性 | 退出码 1，中断构建 |
| 文档级 | `check-doc-sync.mjs` | 硬编码计数/版本、`trailingSlash` 一致性、命令表镜像、多语言债 | 退出码 1，中断构建 |
| 产物级 | `check-links.mjs` | 站内链接落点、各语言页面配对 | 错误中断；`PENDING_ROUTES` / `SINGLE_LOCALE_PAGES` 例外只警告 |
| 布局级 | `check-layout.mjs` | `dist/` 全扫（含 404）：页头→首块内容空带 >72px、横向溢出（clientWidth 口径）、全部 `.btn` 高度/主按钮配色/空文案；桌面隐藏元素不计异常 | 本地硬门：`npm run check:layout 1600` + `390`，退出码 1 |
| 301 级 | `check-redirects.mjs` | 型号旧路径规则完整性；传 `--base` 时逐条验证 301 → 200 → canonical | 退出码 1 |
| 页面级 | `buildMeta()` | 标题后缀与宽度、描述宽度 | 直接抛错 |
| 单测 | `tests/` + `vitest.config.ts` | 规则本身 | `npm run test` 失败 |

细则、节号与失败级别以 `scripts/validate-content.mjs` 的 `/* ---------- N. ... */` 与 `check-links.mjs` 为准；本表不复制逐条规则。

`vitest.config.ts` 固定测试池，原因见该文件注释；不要改回默认池。

**已知取舍：**

- 对比表列与型号键不匹配时，构建不报错，对应单元格渲染 `—`；只有脚本 §1.1/§4 和人工抽查能发现。schema 管不了跨条目关系。
- `datasheet` / `downloads.file` 缺失只警告，不拦截发布；文件常滞后于内容录入，运营按同名补传。

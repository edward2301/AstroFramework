# 开发框架设计

> 项目：B2B 工业品出口站
> 技术栈：Astro 7（`astro` 依赖 `^7.4.2`）· TypeScript strict · Node 24.14.1

---

## 1. 整体架构分层

Astro 的运行模型是「内容 → 构建 → 静态产物」，没有运行期服务端。分层必须匹配这一模型，不能照搬 MVC 或前后端分离那套。

```
┌──────────────────────────────────────────────┐
│  L6  构建层    astro.config · 校验脚本 · Pages 部署 │
├──────────────────────────────────────────────┤
│  L5  页面层    src/pages        路由与组装       │
├──────────────────────────────────────────────┤
│  L4  布局层    src/layouts      页面骨架         │
├──────────────────────────────────────────────┤
│  L3  组件层    src/components   展示与交互       │
├──────────────────────────────────────────────┤
│  L2  数据层    src/lib          仓储与领域逻辑    │
├──────────────────────────────────────────────┤
│  L1  内容层    src/content      数据源与 schema  │
└──────────────────────────────────────────────┘
               横切：SEO · 样式 · 资源
```

### 1.1 各层职责

| 层 | 职责 | 不做什么 |
|---|---|---|
| L1 内容层 | 定义集合、schema、数据文件 | 不写展示逻辑，不做数据加工 |
| L2 数据层 | 仓储（`lib/content`，集合查询/排序/草稿过滤/关联解析）· 载荷装配（`lib/pages`）· SEO（`lib/seo`）· 导航派生（`lib/nav`） | 不产出 HTML，不依赖组件 |
| L3 组件层 | 渲染 UI，接收 props，无副作用 | **不直接读取内容集合** |
| L4 布局层 | 页面骨架（头部、页脚、主区域），把派生好的导航渲染出来 | 不承载业务数据查询 |
| L5 页面层 | 路由枚举与分派（`[...slug].astro`）；静态页数据来自 `data/pages/entries` | 不写可复用的展示逻辑 |
| L6 构建层 | 配置、集成、构建期校验 | 不参与页面渲染 |

### 1.2 核心设计原则

**页面不直接调用 `getCollection`，一律经 `src/lib/content`。**

这是整个框架最重要的一条约束。理由：

- schema 变更时，只需改仓储层，不必全站搜索替换
- 关联解析（替代型号、应用推荐）集中一处，避免各页面各写一遍
- 草稿过滤、排序规则、可见性判断统一，不会漏掉某个页面
- 将来若切换数据源（Git → CMS），只需替换仓储层实现，页面无感知

## 2. 核心模块划分

| 模块 | 位置 | 职责 | 关键产出 |
|---|---|---|---|
| 内容定义 | `src/content.config.ts` | 7 个集合的 loader 与 schema | 类型安全的集合查询 |
| 内容数据 | `src/content/*` | 型号、品类、应用、案例、指南、问答、资料 | 内容源文件 |
| 站点数据 | `src/data/*` | 站名与后缀、组织实体、页脚分区顺序等非集合常量 | 常量与配置 |
| 仓储层 | `src/lib/content/*` | 集合查询、排序、过滤、关联解析 | 语义化查询函数 |
| SEO 引擎 | `src/lib/seo/*` | 元标签生成、结构化数据构造、面包屑 | 每页唯一的 SEO 载荷 |
| 页面条目 | `src/data/pages/*` | 一页一文件：path、SEO、正文、导航落点 | 静态页的唯一登记处 |
| 导航派生 | `src/lib/nav.ts` | 读条目 nav 字段，产出主导航与页脚。同一 URL 只占一个位置——与页眉 CTA 同目标的页面（如询价页）不设 `nav.main` | 全站导航结构 |
| 路由常量 | `src/data/routes.ts` | 从条目 path 派生一级路径与详情拼接 | 全站链接与路由的唯一来源 |
| 载荷装配 | `src/lib/pages/*` | `static.ts` 按版式装静态页，`render.ts` 按集合装内容页 | 每页唯一的渲染载荷 |
| 布局 | `src/layouts/*` | 当前只有 `BaseLayout`（唯一骨架） | 页面外壳 |
| 布局组件 | `src/components/layout/*` | 头部、页脚、PageHeader、Carousel（轮播）、CtaBand | 骨架组件 |
| 卡片组件 | `src/components/cards/*` | CategoryCard / ModelCard（轮播卡）、CategoryRow（总览图文横排） | 可复用的内容卡，交互规则内聚 |
| 页面主体 | `src/components/pages/*` | 各类版式的 Body 组件（HomeBody · ModelBody …） | 只渲染，不取数 |
| SEO 组件 | `src/components/seo/*` | 输出 meta、JSON-LD | 无渲染的头部注入 |
| 构建校验 | `scripts/*` | 内容体检、链接检查 | 构建失败的拦截 |

> `components/ui` / `product` / `content`、`layouts/ProductLayout` 等目录
> 一律不预先建立空目录。

### 3.1 命名约定

| 对象 | 规则 | 示例 |
|---|---|---|
| 集合目录 | 复数、小写、连字符 | `models/` `cases/` |
| 内容文件 | 与 URL slug 一致 | `a1.json` → `/products/category-a/a1/`；`guides/install-checklist.md` → `/resources/guides/install-checklist/` |
| Astro 组件 | PascalCase | `ModelCard.astro` |
| 布局 | 后缀 `Layout` | `BaseLayout.astro`（当前唯一布局） |
| 工具模块 | 小写、按域分组 | `lib/content/models.ts` |
| 查询函数 | 动词开头、语义化 | `getModelsByCategory()` |

### 3.2 目录范围

只为实际使用的模块建目录，不预留空目录与占位组件。`BaseLayout` 提供全站骨架（头部、页脚、SEO 出口），业务结构留在页面内；品类页与型号页除面包屑与页面级样式外没有共用结构，不需要第二层布局。

`dist/404.html` 与 `dist/zh/404.html` 各一份、`noindex`（后者由构建守卫从 `dist/zh/404/index.html` 复制，供 Pages 按前缀就近查找）。资料下载由 `static.ts` 的 `sectionContent()` 读 `downloads` 集合渲染列表，列表项直达 `file` 字段。

未实现的路径登记在 `scripts/check-links.mjs` 的 `PENDING_ROUTES` 中，构建只警告不阻断；未登记的断链会让构建失败。

## 4. 模块依赖关系

### 4.1 依赖方向

```
src/pages ──▶ src/layouts ──▶ src/components ──▶ src/lib/utils
    │              │               │
    │              ▼               ▼
    └────▶ src/lib/seo              src/data/  (pages/entries · navigation · site · organization)
    │              ▲
    └────▶ src/lib/pages ──▶ src/lib/content ──▶ src/content/  (L1)
                 │
                 └──▶ src/lib/nav（读 src/data/pages 的 nav 字段）
```

`src/pages` 依赖 `src/lib/*` 时经 `src/lib/pages/{static,render}.ts` 统一进 `src/lib/content` 与 `src/lib/seo`：
`static.ts` 按版式装静态页（数据来自 `src/data/pages/entries/`），`render.ts` 按集合装内容页；
导航由 `src/lib/nav.ts` 从页面条目派生，布局层只把它渲染出来。
路由文件 `[...slug].astro` 本身只做路径分发，不直接写装配逻辑。

### 4.2 允许与禁止

| 模块 | 可依赖 | **禁止依赖** |
|---|---|---|
| `pages` | `layouts` `lib/*` `data/*` | 不得被任何模块依赖 |
| `layouts` | `components/*` `lib/seo` `data/*`、**`lib/content/site`** | 不得调用 `getSiteNav()` 以外的任何内容查询 |
| `components` | `lib/utils` `data/*` | **不得依赖 `lib/content`**（数据一律由 props 传入） |
| `lib/content` | `content.config` `lib/utils` | 不得依赖任何组件或布局 |
| `lib/seo` | `data/site` `data/organization` `data/navigation` `lib/utils` | 不得依赖 `lib/content` |
| `lib/pages` | `lib/content` `lib/seo` `data/pages` `data/navigation` `i18n/*` | 不写展示标记 |
| `lib/nav` | `data/pages` `data/navigation` `i18n/*` | 不硬编码任何链接 |
| `data` | `i18n`（仅 type）、同目录文件 | 不得依赖 `lib/*` 与任何组件 |

> **布局层的唯一例外**：`BaseLayout` 需要品类与应用方向来渲染导航与页脚，这类数据属于站点结构而非页面业务数据。若逐页取数再透传，每个页面都会背上一段与自身无关的查询。因此 `src/lib/content/site.ts` 单独暴露 `getSiteNav()`，布局层只允许调用这一个函数。

> **组件的类型例外**：`Breadcrumb.astro` 从 `src/lib/seo/breadcrumb` 导入 `Crumb` 类型，属 type-only 依赖，不产生运行期耦合。组件不得从 `src/lib/seo` 导入任何函数或值。

### 4.3 三条硬性规则

**规则一：组件不取数。**
`src/components/**` 内不出现 `getCollection` / `getEntry`。所有数据由页面或布局通过 props 传入。这样组件可在任意上下文复用，也便于单独调试。

**规则二：页面不手写 SEO 标签，但可以提供文案。**

页面里不出现 `<title>`、`<meta name="description">`、`<script type="application/ld+json">`。全部经 `BaseLayout` → `<SEO>` 与 `<JsonLd>` 输出。

文案的来源分两种：内容页取该条内容自带的 `seoTitle` / `seoDescription`；栏目页与首页在页面内声明，但**必须经 `buildMeta()` 处理**——它负责补品牌后缀并把长度不合规变成构建失败。页面直接写标签则绕过了这道关口。

**规则三：关联不在展示层解析。**
正向关联（型号的 `replacement` / `applications` / `relatedCases`）由 `src/lib/content/models.ts` 的 `getModelDetail()` 用 `getEntries()` 解析成完整对象；`src/lib/content/relations.ts` 只负责**反向关联**（某型号被哪些 `applications.recommended` / `cases.config` 引用），用一次遍历建 `Map<modelId, BacklinkIndex>`，由 `getModelBacklinks()` 查询。两者都在仓储层完成，模板里不做二次查询。

## 5. 内容层设计

### 5.1 集合定义

配置文件为 `src/content.config.ts`（非 `src/content/config.ts`）。

> 以下为 schema 的主要约束（完整定义见 `src/content.config.ts`）：

```ts
// src/content.config.ts
import { defineCollection, reference } from 'astro:content';
import { glob } from 'astro/loaders';
import { z } from 'astro/zod';

/** 型号 */
const models = defineCollection({
  loader: glob({ base: './src/content/models', pattern: '**/*.json' }),
  schema: z.object({
    draft: z.boolean().default(false),
    code: z.string().min(2),                              // 型号编码，如 A1
    name: z.string().min(2),
    category: reference('categories'),
    status: z.enum(['active', 'discontinued']),           // 在售 / 停产
    replacement: z.array(reference('models')).default([]),   // 替代型号，单向声明
    keyParams: z.array(z.object({ k: z.string(), v: z.string() })).length(5),
    specGroups: z.array(z.object({
      title: z.string(),
      rows: z.array(z.object({ k: z.string(), v: z.string() })).min(1),
    })).min(1),
    dimensions: z.string().optional(),
    interface: z.string().optional(),
    certifications: z.array(z.string()).default([]),
    datasheet: z.string().optional(),                     // public/ 下的路径
    image: z.string().optional(),                         // 主图，public/ 下的路径
    applications: z.array(reference('applications')).default([]),
    relatedCases: z.array(reference('cases')).default([]),
    seoTitle: z.string(),
    seoDescription: z.string(),

    /** 各语言译文，键为 LOCALES 中的语言代码；partialRecord 让每种语言都可不提供 */
    locales: z.partialRecord(z.enum(LOCALES), z.object({
      name: z.string().optional(),
      keyParams: z.array(z.object({ k: z.string(), v: z.string() })).length(5).optional(),
      specGroups: z.array(z.object({
        title: z.string(),
        rows: z.array(z.object({ k: z.string(), v: z.string() })).min(1),
      })).min(1).optional(),
      seoTitle: z.string().optional(),
      seoDescription: z.string().optional(),
    })).optional(),
  }),
});

/** 品类 */
const categories = defineCollection({
  loader: glob({ base: './src/content/categories', pattern: '**/*.json' }),
  schema: z.object({
    draft: z.boolean().default(false),
    name: z.string(),
    intro: z.string().min(300),                           // 品类定义 ≥300 字符
    image: z.string().optional(),                         // 品类封面，public/ 下的路径
    comparisonParams: z.array(z.string()).min(5).max(7),   // 对比表列，5–7 项
    selectionPoints: z.array(z.string()).default([]),
    purchaseInfo: z.object({
      moq: z.string(),
      leadTime: z.string(),
      payment: z.string(),
      certifications: z.array(z.string()).default([]),
    }),
    order: z.number().default(100),
    seoTitle: z.string(),
    seoDescription: z.string(),
  }),
});

/** 应用方向 */
const applications = defineCollection({
  loader: glob({ base: './src/content/applications', pattern: '**/*.json' }),
  schema: z.object({
    draft: z.boolean().default(false),
    name: z.string(),
    condition: z.string(),
    criteria: z.array(z.string()).min(1),
    recommended: z.array(reference('models')).min(2).max(5),
    cautions: z.array(z.string()).default([]),
    seoTitle: z.string(),
    seoDescription: z.string(),
  }),
});

/** 案例 */
const cases = defineCollection({
  loader: glob({ base: './src/content/cases', pattern: '**/*.json' }),
  schema: z.object({
    draft: z.boolean().default(false),
    title: z.string(),
    background: z.string(),
    requirements: z.array(z.string()).min(1),
    selection: z.string(),
    config: z.array(reference('models')).min(1),         // 实际配置清单
    results: z.array(z.string()).default([]),
    date: z.coerce.date(),
    seoTitle: z.string(),
    seoDescription: z.string(),
  }),
});

/** 指南：Markdown 正文 + frontmatter；语言按目录分文件，无 locales、无跨语言回落 */
const guides = defineCollection({
  loader: glob({ base: './src/content/guides', pattern: '**/*.md' }),
  schema: z.object({
    draft: z.boolean().default(false),
    title: z.string(),
    tldr: z.string(),
    updated: z.coerce.date(),
    relatedModels: z.array(reference('models')).default([]),
    relatedApplications: z.array(reference('applications')).default([]),
    seoTitle: z.string(),
    seoDescription: z.string(),
  }),
});

/** 问答（语言同样按目录区分：faqs/*.md 与 faqs/zh/*.md） */
const faqs = defineCollection({
  loader: glob({ base: './src/content/faqs', pattern: '**/*.md' }),
  schema: z.object({
    draft: z.boolean().default(false),
    question: z.string(),
    cluster: z.enum(['selection', 'params', 'install', 'troubleshoot']),
    relatedModels: z.array(reference('models')).default([]),
    relatedFaqs: z.array(reference('faqs')).default([]),
    seoTitle: z.string(),
    seoDescription: z.string(),
  }),
});

/** 资料。gated 决定是否需留资获取，文件位于 public/ 下 */
const downloads = defineCollection({
  loader: glob({ base: './src/content/downloads', pattern: '**/*.json' }),
  schema: z.object({
    draft: z.boolean().default(false),
    title: z.string(),
    docType: z.enum(['datasheet', 'manual', 'drawing', 'certificate']),
    version: z.string(),
    updated: z.coerce.date(),
    model: reference('models').optional(),
    gated: z.boolean().default(false),
    file: z.string(),
  }),
});

export const collections = {
  models, categories, applications, cases, guides, faqs, downloads,
};
```

**要点说明：**

- `keyParams` 固定为 5 项，与架构方案「首屏给 5 个决定性参数」一致
- `comparisonParams` 限定 5–7 项，与「对比表列 5–7 个参数」一致
- `intro` 限定 ≥300 字，把品类页的厚度要求写入 schema，而不是靠人工检查；译文 `intro` 下限 150 字
- 译文子 schema 共 4 个（型号 / 品类 / 应用 / 案例），逐字段 `.optional()`；`guides` / `faqs` 按 `zh/` 目录分文件，`downloads` 只有可选 `locales.<lang>.title` 且无独立 SEO 字段
- `recommended` 限定 2–5 个，对应应用方向页「推荐 2–5 个型号」
- `status` 与 `replacement` 配合，处理停产型号：停产型号仍生成页面，但必须从品类页获得入口
- 7 个集合统一带 `draft`，仓储层在查询与关联解析时一并排除；已发布条目引用草稿会在校验阶段报错
- `seoTitle` 只写标题本体，品牌后缀由 `buildMeta()` 统一追加，避免换品牌时全量改内容

**两条必须成对理解的约束：**

**其一，`comparisonParams` 与 `keyParams` 的键名必须对得上。** 品类声明「对比哪些列」，型号的 `keyParams` 提供「每一列的值」，渲染时按 `k` 字段匹配。品类写 `IP Rating`、型号写 `Protection`，对比表就会渲染出一整列空白——**构建不报错，页面也看得见，只有人工逐页检查才会发现**。这条跨条目的约束写在 `scripts/validate-content.mjs` 里（§8.4 第 5 项）。

**其二，`seoTitle` 与 `seoDescription` 由编辑撰写，不做模板拼接。** 六个集合都带这两个字段，只保留 `downloads` 例外——它仅出现在资料列表页，不单独成页。

不拼接的理由是实测过的：按模板拼 `{型号编码} {品类名} — {参数}`，300 个型号会产出 300 条结构雷同的标题，既无区分度，长型号还会在拼接后被截断成残句。编辑撰写 + 机器校验长度与唯一性，比机器生成 + 人工抽查更可控。`src/lib/seo/meta.ts` 只负责补品牌后缀与长度把关，不参与文案创作。

### 5.2 存储格式选择

| 内容 | 格式 | 理由 |
|---|---|---|
| 型号、品类、应用、案例、资料 | JSON | 字段密集、以结构化数据为主，正文叙述短 |
| 指南、问答 | Markdown | 以长文正文为主，需要富文本与排版 |

同一条内容不混用两种格式。型号页的叙述性内容放在 `specGroups` 之外的字段里，不进 Markdown。

### 5.3 仓储层

> 以下为仓储层的查询约定（完整实现见 `src/lib/content/models.ts`）：

```ts
// src/lib/content/models.ts
import { getCollection, getEntries, getEntry } from 'astro:content';

/** 按品类取型号，排除停产与草稿（除非显式要求） */
export async function getModelsByCategory(categoryId: string, includeDiscontinued = false) {
  const all = await getCollection('models', ({ data }) =>
    !data.draft &&
    data.category.id === categoryId &&
    (includeDiscontinued || data.status === 'active')
  );
  return all.sort((a, b) => a.data.code.localeCompare(b.data.code));
}

/** 取型号并附带已解析的关联对象（草稿不出现） */
export async function getModelDetail(id: string) {
  const entry = await getEntry('models', id);
  if (!entry || entry.data.draft) return null;

  const [replacements, applications, cases] = await Promise.all([
    entry.data.replacement.length ? getEntries(entry.data.replacement) : [],
    entry.data.applications.length ? getEntries(entry.data.applications) : [],
    entry.data.relatedCases.length ? getEntries(entry.data.relatedCases) : [],
  ]);

  // 被引用的条目可能是草稿，草稿不应出现在已发布页面上
  const published = <T extends { data: { draft: boolean } }>(list: T[]) =>
    list.filter((item) => !item.data.draft);

  return {
    ...entry,
    replacements: published(replacements),
    applications: published(applications),
    cases: published(cases),
  };
}
```

**草稿过滤落在两处：** 查询入口用 `!data.draft` 排除草稿自身；关联对象（替代型号、应用方向、案例）解析后再经 `published()` 过滤一次——已发布条目的 `replacement` / `applications` / `relatedCases` 可能指向草稿，而草稿不应出现在已发布页面上。

页面调用。内容页只有 `src/pages/[...slug].astro` 一个分发路由（404 另有 `404.astro` 与 `[lang]/404.astro`，`robots.txt.ts` 单独产出），`getStaticPaths()` 遍历
`LOCALES` × (页面条目 + 各集合) 产出全部路径；入口只有 `loadPage` 一个，
静态页与内容页的分派在 `src/lib/pages/` 内部完成：

```astro
---
// src/pages/[...slug].astro（节选：仅示静态页与型号分支；实际在 LOCALES 循环外一次性取数，notFound 版式在此 continue 跳过）
import { loadPage, toSlug, type PageInput } from '../lib/pages/render';
import { publishedPageEntries } from '../data/pages';
import { detailPath } from '../data/routes';

export const getStaticPaths = (async () => {
  const entries: { params: { slug?: string }; props: PageInput }[] = [];
  for (const locale of LOCALES) {
    // ① 静态页：路径写在页面条目里，新增栏目不需要改这里
    for (const { id, def } of publishedPageEntries()) {
      entries.push({
        params: { slug: toSlug(locale, def.path) },
        props: { kind: 'static', pageId: id, locale },
      });
    }
    // ② 内容页：路径由集合条目拼出（斜杠规则只在 detailPath 一处）
    for (const m of await getAllModels(true)) {
      entries.push({
        params: { slug: toSlug(locale, detailPath.model(m.data.category.id, m.id)) },
        props: { kind: 'model', locale, categoryId: m.data.category.id, modelId: m.id },
      });
    }
  }
  return entries;
}) satisfies GetStaticPaths;

const page = await loadPage(Astro.props as PageInput);
---
```

`loadPage` 收到 `kind: 'static'` 时转 `static.ts` 按版式装配，其余 kind 由 `render.ts` 按集合装配。

页面**不出现** `getCollection`，只经 `src/lib/pages` 的装配函数调仓储层。将来若改为从 CMS 取数，只替换仓储层实现。

**一处容易写错的地方：不要用 `Astro.redirect('/404')` 处理取不到的情况。** 静态模式下 `redirect` 会在该路径生成一个带 meta refresh 的跳转页，它既不是 404 状态码，也不会被搜索引擎当作不存在处理；而路径本身是由 `getStaticPaths` 生成的，取不到只可能是数据不一致。正确做法是抛错（`static.ts` / `render.ts` 中已如此），让构建停在数据问题上。

### 5.4 多语言

**路由结构：默认语言不带前缀，中文带 `/zh`。**

```
/products/category-a/a1/       英文
/zh/products/category-a/a1/    中文
```

不采用 `/en/` + `/zh/` 双前缀：英文站是面向海外买家的主站，根路径即英文可以少一层跳转，也不会让既有外链与收录历史失效。

**内容 slug 两种语言共用。** 翻译 slug 会产出两套 URL 体系，收益仅是外观，代价是重定向表、内链重写、以及 slug 一致性校验要按语言各写一套。

**四层文案，各有归属。** 完整分层表（哪层放哪、由谁维护）见 `docs/上手指南.md` §5.2，此处只讲为什么分开：

分开的理由很实际：运营改一句产品描述，不该需要动代码；开发改一个按钮文案，也不该去翻 300 个 JSON。

**两种翻译结构，按内容形态分工。** 这一点必须写死，否则两种存法会互相渗透：

| 内容形态 | 集合 | 翻译存放方式 | 理由 |
|---|---|---|---|
| 参数型 | `models` `categories` `applications` `cases` | 同一文件内嵌 `locales[语言]` 对象 | 参数数值必须唯一。两套语言记录各自维护数值，迟早出现「英文 1.6MPa、中文 1.5MPa」这种对照不上、却都能通过校验的情况 |
| 正文型 | `guides` `faqs` | 一个语言一个文件：`foo.md` 与 `zh/foo.md` | 正文是页面主体，要和结构化字段一起被当作独立篇章收录。正文塞进 frontmatter 既不可读，也没法做语法高亮与相对图片引用 |

正文型的语言由**目录前缀**表达（`routing.ts` 的 `localeOfEntryId`），schema 无 `locale` 字段——少一个字段就少一处写错的机会。缺某个语言的文件时，**该语言页面根本不生成**，而不是拿源语言正文凑一个页面出来。

两种结构共用的约束：标题与描述必须各语言独立撰写，不得互译照抄——同一句话翻两遍的 `title` 会被判重复，跨语言查重由构建脚本统一拦截。

**译文：语言块必填，必填字段不可分批。** 参数型集合的 `locales` 里只要出现了某一语言，`REQUIRED_TRANSLATION` 列出的必填字段就必须齐全；没有该语言块则构建失败。`dimensions`、`interface` 等补充字段不在必填表内，缺失时直接回落源语言，**不报错也不告警**。正文型集合由「配对校验」把关：每个 slug 必须在每个语言下都有文件，缺一个即构建失败，报错直接给出应新建的路径。理由见下一条。

**视图函数按语言键查表，不判断具体语言。** `categoryView(entry, locale)` 内部只做 `entry.data.locales?.[locale]`，无论现有两种语言还是将来五种，都不存在「漏写某个语言的判断分支」。按具体语言写判断分支时，新语言会**静默**渲染源语言内容——构建通过、链接正确、页面全英文，比链接跳错更难发现。

**缺译是错误，不是告警。** 缺少某一语言块会直接中止构建，报错写明缺哪个条目、缺哪种语言。想「先出英文后补译文」的正确做法是不发布该语言的这个页面，而不是带着源语言内容上线。

**页面只传语言无关路径。** 页面写 `path="/products/"`，布局据此推导 canonical、hreflang、`<html lang>`、`og:locale`。页面自己拼前缀会导致三种来源的地址不一致，而这在产物里看不出异常。

**为什么中英文页面共用一套 body 组件：** 若各写一份，改一处 UI 要改两处，第二处迟早漏。单路由分发器 + `src/lib/pages` 的装配函数只做「取数 → 拼 SEO → 传参」，渲染全在 `src/components/pages/*Body.astro`。

`content.config.ts` 导出 4 个 `locales` 子 schema（`modelLocales` / `categoryLocales` / `applicationLocales` / `caseLocales`），`localize.ts` 的 `translationOf()` 用 `z.output<S>` 派生译文类型——schema 改字段时视图的编译会跟着变，不会出现两份手写副本漂移。

404 每种语言各一份：默认语言由 `src/pages/404.astro` 产出 `dist/404.html`（Cloudflare Pages 根目录 404 约定），其余语言由 `src/pages/[lang]/404.astro` 按 `LOCALES`（排除默认语言）产出，不经 `[...slug].astro` 分发器——该分发器在静态页循环里对 `layout === 'notFound'` 直接 `continue`。分语言 404 的复制与就近查找机制属运维细节，见 `deploy/cloudflare/README.md` 的「分语言 404」一节。
页脚与询价页的公司地址、`Organization` 描述来自 `src/data/organization.ts`：
`locales.zh` 提供中文 `description` 与 `address`，`organizationFor(locale)` 按语言返回；
`name` / `legalName` / `contactPoint` / `sameAs` 不翻译。

## 6. SEO 层设计

SEO 是横切关注点，不归属某一层，但必须有唯一出口。

### 6.1 单一入口

```astro
---
// src/components/seo/SEO.astro
import { SITE } from '../../data/site';
import { absoluteUrl } from '../../lib/seo/meta';
import { LOCALE_META, type Locale } from '../../i18n/routing';

interface Props {
  title: string;                                  // 已含品牌后缀，由 buildMeta 产出
  description: string;
  canonical: string;                              // 相对路径，已含语言前缀，如 /zh/products/category-a/
  image?: string;
  noindex?: boolean;
  ogType?: 'website' | 'article' | 'product';
  locale: Locale;
  alternates: { hreflang: string; path: string; ogLocale: string }[];
}

const { title, description, canonical, image = SITE.ogImage,
        noindex = false, ogType = 'website', locale, alternates } = Astro.props;
const canonicalUrl = absoluteUrl(canonical);
const imageUrl = absoluteUrl(image);
const meta = LOCALE_META[locale];
---
<title>{title}</title>
<meta name="description" content={description} />
{/* noindex 页（404）不输出 canonical 与 og:url */}
{!noindex && <link rel="canonical" href={canonicalUrl} />}
{alternates.map((alt) => (
  <link rel="alternate" hreflang={alt.hreflang} href={absoluteUrl(alt.path)} />
))}
{noindex && <meta name="robots" content="noindex, follow" />}

<meta property="og:type" content={ogType} />
<meta property="og:site_name" content={SITE.name} />
<meta property="og:title" content={title} />
<meta property="og:description" content={description} />
{!noindex && <meta property="og:url" content={canonicalUrl} />}
<meta property="og:image" content={imageUrl} />
<meta property="og:locale" content={meta.ogLocale} />
{alternates
  .filter((alt) => alt.hreflang !== 'x-default' && alt.hreflang !== meta.htmlLang)
  .map((alt) => <meta property="og:locale:alternate" content={alt.ogLocale} />)}
<meta name="twitter:card" content="summary_large_image" />
<meta name="twitter:title" content={title} />
<meta name="twitter:description" content={description} />
<meta name="twitter:image" content={imageUrl} />
```

**三个设计取舍：**

- **绝对地址走 `absoluteUrl()` 而不是 `new URL(x, Astro.site)`。** `Astro.site` 只在组件与页面的作用域内可用，`src/lib/seo` 里的 schema 构造拿不到它；把域名解析收在 `absoluteUrl()` 一处，组件与数据层才能共用同一套规则。域名本身来自 `import.meta.env.SITE`（§8.3）。
- **组件只管输出，不管校验。** 长度与唯一性的把关在 `buildMeta()` 与校验脚本里完成；`SEO.astro` 若再校验一遍，同一规则就有两个实现，迟早不一致。
- **`title` 必须是已含后缀的完整标题。** 组件不做后缀补全——否则「谁负责拼后缀」这件事会分散到每个调用方。

**`noindex` 页（404）不输出 hreflang。** `BaseLayout` 在 `noindex` 时把 `alternates` 置空——404 不是「某页面的语言版本」，强行声明会指向未生成路径；`SEO.astro` 只对 canonical / `og:url` 做条件判断。

### 6.2 生成与校验分离

校验分两层，责任人不同：

| 层 | 位置 | 管什么 | 失败方式 |
|---|---|---|---|
| 页面级 | `src/lib/seo/meta.ts` 的 `buildMeta()` | 标题后缀补全、标题与描述的长度 | **直接抛错**，中断构建 |
| 内容级 | `scripts/validate-content.mjs` | 标题全站唯一、引用完整性、编码与文件名一致、对比表列覆盖 | 退出码 1，中断构建 |

**页面级为什么要抛错而不是返回 issues：** 返回数组、由调用方决定要不要处理，这种 API 在真实项目里一定会被忽略（只打一行日志）。长度不合规的页面不应该进入产物，因此校验即失败点，没有「先放过」的选项。

**内容级为什么必须独立成脚本：** 它依赖跨条目的关系——同一标题是否在别的文件里出现过、`replacement` 指向的型号是否存在、品类的对比列是否被每个型号覆盖。zod 只能校验单个条目，跨条目规则写不进 schema。

两层都在构建期执行。Astro 的页面渲染发生在构建时，运行期没有断言机会；把关卡放在产物生成之前，是唯一能保证「不合格内容进不了产物」的位置。

## 7. 技术约束

### 7.1 强制项

| # | 约束 | 检查方式 |
|---|---|---|
| 1 | 所有集合必须定义 schema，不得使用 `z.any()` | 代码评审 |
| 2 | 组件内不得出现 `getCollection` / `getEntry` | 代码评审 |
| 3 | 页面不手写 `<title>` / `<meta>` / JSON-LD | 结构保证：页面不直接写 `<head>`，只有 `BaseLayout` 输出 |
| 4 | 标题（含品牌后缀后）50–60、描述 140–158（**按显示宽度，全角计 2**） | 页面级 `buildMeta` 抛错 + 脚本校验 |
| 5 | 标题全站唯一 | 脚本校验 |
| 6 | 图片放 `public/images/…`，用裸 `<img>`，不做构建期处理（见 §7.5） | 脚本校验 `width`/`height`/`alt`/`loading` 与文件存在性 |
| 7 | 每页唯一 `<h1>` | 代码评审 |
| 8 | 每个内容页必须有可见面包屑 | 页面同时输出 `Breadcrumb` 组件与 `breadcrumbSchema`，共用同一 `crumbs` 数组 |
| 9 | 不存在的路由返回 404 | 静态产物不含多余路径，`public/_redirects` 不得配 SPA fallback；按 `deploy/cloudflare/README.md` 的 5 条 curl 实测 |

**关于第 4 项的 50–60：** 这个区间来自站点元标签规范，同时给出了 7 类页面的标题公式。区间下限不是排版偏好，而是信息完整度的代理指标——标题低于 50 字符，通常意味着少了量程、精度、防护等级或认证中的一项。占位品牌名较短时标题容易落到 48–49，此时应补一项真实参数，而不是放宽下限：放宽会让「参数不全」的标题同样通过。

### 7.2 TypeScript

- 继承 `astro/tsconfigs/strict`（已配置）
- 禁止 `any`；不确定类型用 `unknown` 并收窄
- 集合查询结果不得断言为非空。动态路由用 `getStaticPaths()` 生成全部路径，页面内取不到条目时**抛错中断构建**，不用 `Astro.redirect('/404')`（静态模式下它产出跳转页，不是 404）

### 7.3 运行环境

**本项目固定使用 Node 24.14.1。** Astro 7 的硬性下限是 22.23.4（`node_modules/astro/package.json` 的 `engines` 字段），低于此版本 `astro build` 直接拒绝执行。选择 24.14.1 而非贴着下限运行，是因为 LTS 线内的更高小版本在 ESM 加载与类型解析上更稳定。

版本在三处同时锁定，任何一处缺失都会让新环境回落到宿主机默认值：

| 位置 | 值 | 作用 |
|---|---|---|
| `.nvmrc` | `24.14.1` | nvm / fnm 切换依据 |
| `.node-version` | `24.14.1` | asdf / volta / mise 识别 |
| `package.json` → `engines.node` | `^24.14.1` | 安装期约束，允许 24.x 内升级，不允许跨大版本 |

**开发机已知问题：** 若默认 PATH 上的 `node -v` 低于 22.23.4，直接执行 `npm run build` 会报 `Node.js vXX is not supported by Astro`。这是环境问题，不是代码问题——先 `nvm use`（或 fnm / volta）切到 24.14.1 再构建，不要据此改代码。

仅当版本管理器不可用时临时指定（PowerShell）：

```powershell
$env:Path = "C:\Program Files\nodejs;$env:Path"
```

Cloudflare Pages 构建环境必须显式声明 Node 版本（读取 `.nvmrc`，或在 Pages 构建配置里设置环境变量 `NODE_VERSION=24.14.1`），不得依赖构建机默认值；CI 环境同理。

### 7.4 禁止事项

- 不使用双套 DOM 实现响应式（桌面表格 + 移动卡片）
- 不在客户端引入框架运行时，除非确有交互需求
- **客户端交互脚本共三段，无框架、只处理交互**：
  1. 轮播（`src/components/layout/Carousel.astro`，普通 `<script>`，由 Astro 打包）：卡片全部在服务端 HTML 里，脚本只控制
     「看哪几张」——滚动、箭头禁用态、分页页码；不加载内容、不产生新 URL。支持一页多实例。
     无 JS 时箭头与分页隐藏，卡片仍可滑动（纯 CSS scroll-snap）。
  2. 页眉滚动状态（`Header.astro` 的 `is:inline` 脚本，仅首页 overlay 变体渲染）：滚动超过阈值后把透明浮层切换成白底黑字，
     否则白字会压在白底内容上。
  3. 询价表单（`src/components/pages/QuoteBody.astro` 的普通 `<script>`）：必填项与邮箱格式校验、防重复提交、
     按 `data-mailto` 拼 mailto 并显示回落链接；不提交到服务端。
  `JsonLd.astro` 里的 `<script type="application/ld+json" is:inline>` 是结构化数据，不属于交互脚本。
  新增客户端交互前先问：能不能用纯 CSS（scroll-snap / details / :hover）达成
- 不让构建处理图片（转码、生成多尺寸）：那是运营上传前的事，见 §7.5
- 不为「将来可能用到」预留空目录与空模块

### 7.5 图片与静态资源

**图片是运营资产，不经过构建处理。** 构建只做一件事：把 `public/` 原样复制进 `dist/`。

```
public/images/models/a1.png          ← 运营按编码放图，一图一名
src/content/models/a1.json           "image": "/images/models/a1.png"
src/components/pages/ModelBody.astro         <img src={image} …>
```

**为什么不进构建管线：**图片本就该在上传前压好。一旦让构建去转 WebP、生成多尺寸，构建时间就会随图片数量线性增长，而且每次构建都重算一遍——可绝大多数构建里图片根本没变，重算是纯浪费。

**运营需要遵守的四条：**

| 项 | 要求 |
|---|---|
| 路径 | `public/images/models/<型号编码>.png`（或 `.webp`），一图一名；多图加序号后缀（`a1-2.png`） |
| 尺寸 | 黄金比 1.618:1，800×494（页面按 1.618 预留位置，比例不同只会轻微跳动） |
| 体积 | ≤ 100 KB，优先 WebP |
| 替换 | 同名覆盖即可，不改代码、不动 JSON |

**程序这边保证的四条：**

| 项 | 做法 |
|---|---|
| 宽高 | `<img>` 手写 `width`/`height`（黄金比 1.618），防布局跳动 |
| alt | 型号 + 产品名，跟随译文 |
| 首屏加载 | `loading="eager"` + `fetchpriority="high"` + `decoding="async"` |
| 路径写错 | `validate` 检查 `public/` 下文件是否存在；`image` 可缺省，填写后文件不存在才判错（`ModelBody` 为条件渲染，缺图不输出 `<img>`）；`datasheet` / `downloads.file` 缺失为告警、页面不输出对应链接 |

**已知取舍：**只有一档图，手机和桌面下同一张。图已压到 ≤100 KB 时，多下几十 KB 比维护三套尺寸便宜。要做响应式就得回到"构建期生成多尺寸"，那是另一个方向。

**示例：型号页主图**

```astro
{image && (
  <img
    src={image}
    alt={`${model.code} ${model.name}`}
    width="800"
    height="494"
    loading="eager"
    fetchpriority="high"
    decoding="async"
  />
)}
```

**校验（`scripts/validate-content.mjs`）**

| 规则 | 级别 |
|---|---|
| `image` 填写后，指向的文件在 `public/` 下存在 | 错误（填写即输出 `<img>`，缺图即破图；`image` 缺省不判错） |
| 任何 `<img>` 必须带 `width` / `height` / `alt` / `loading` | 错误 |

扫描前会屏蔽注释（`<!-- -->`、`/* */`、独占一行的 `//`），避免注释里提到 `<img>` 时误报。

**与 SEO 的对接：**`Product.image` 与 `og:image` / `twitter:image` 自动取这张图的绝对 URL（`https://example.com/images/...`）；没有图的页面回落到 `SITE.ogImage`。图片已在 HTML 里，常规抓取能发现，无需图片 sitemap。

## 8. 配置规范

### 8.1 内容写入路径

**决策：纯文件管理，不引入 CMS。**

- 型号、品类、应用、案例、资料：JSON 文件
- 指南、问答：Markdown 文件
- 全部内容随代码同仓；发布用 `npm run deploy`（构建后经 Wrangler 上传到 Cloudflare Pages），也可在 Pages 配置 Git 集成自动构建，两者跑同一个 `npm run build`

选择理由：

1. 内容由运营逐个添加，起始量级很小，不存在批量导入需求
2. 文件形式天然具备版本追溯与回滚能力，无需额外投入
3. 数据层已隔离在 `src/lib/content`，若将来确需可视化后台，只需替换这一层，页面与组件不受影响

**格式分流的依据：** 型号类内容的本质是结构化参数，而非叙述文本。用 JSON 可获得编辑器的字段提示与类型校验；用 Markdown 存多层嵌套的参数数组，缩进与转义极易出错。指南与问答以长文为主，Markdown 更合适。

同一类内容不混用两种格式。型号页的叙述性内容放在 JSON 字段中，不进 Markdown。

### 8.2 样式方案

| 方案 | 优势 | 劣势 |
|---|---|---|
| Tailwind | 与 Astro 集成好，设计一致性易保证 | 需构建依赖，模板类名较长 |
| 原生 CSS + 变量 | 零依赖，产物最小 | 需自行建立设计系统 |
| CSS Modules | 作用域隔离 | 复用设计变量较繁琐 |

**原生 CSS + 设计变量**（`src/styles/tokens.css` + `global.css`）。本项目版式为 6 种静态版式（`contract.ts` 的 `PageDef` 联合）+ 6 个内容 kind，合计对应 12 个 Body 组件，设计系统规模可控；无构建依赖也更契合性能目标。若团队已熟悉 Tailwind，可整体替换，不影响分层结构。

**色板与字号**（以下为 `tokens.css` 当前值，白底；设计来源是参考站 soukacatv.com 的实测值）：

| 令牌 | 值 | 用途 |
|---|---|---|
| `--color-brand` | `#1863dc` | 按钮、链接、h2 竖条 |
| `--color-brand-hover` | `#0056a7` | 主色悬停 |
| `--color-brand-soft` | `#eaf1fc` | 主色浅底 |
| `--color-text` | `#1c2430` | 正文与标题 |
| `--color-text-muted` | `#626b78` | 次要说明文字 |
| `--color-border` | `#e3e7ed` | 边框与分隔线 |
| `--color-bg-subtle` / `--color-surface` | `#f5f7fa` | 分区浅灰背景 |
| `--fs-h1 / h2 / h3` | `40 / 28 / 18 px` | 标题层级（移动端 30 / 23） |
| `--fs-lead` | `19px` | 首屏导语 |
| `--container` / `--space-8` | `1400px` / `64px`（移动端 44px） | 容器宽度与板块上下间距 |

板块标题（全站 h2）统一带 4px 品牌色竖条（`global.css` 的 `h2::before`），
文章正文里的 h2 同样式，全站一致。改主色只动 `--color-brand` 系列，按钮、链接与竖条自动跟随。

### 8.3 astro.config.mjs

配置全文以 `astro.config.mjs` 为唯一来源。按 §3「不写需要人肉维护的第二份真相」的约定，
本节只写**约束与设计意图**，不复制代码。

配置要点：

- `site` 必须填写真实域名，否则本应在构造时就报错而不是产出占位地址。**它是域名的唯一来源**：`src/lib/seo/meta.ts` 通过 `import.meta.env.SITE` 读取，各模块不另存副本。域名出现多个副本时，改一处漏一处会让 canonical、og:url、JSON-LD 与 sitemap 分属两个域，而这种错误在产物里看不出异常。
- `trailingSlash: 'always'` 与架构方案的「末尾统一带斜杠」一致
- `build.format: 'directory'` 生成目录式产物，便于 Cloudflare Pages 按路径前缀就近查找 `404.html`
- `i18n` 全部取自 `src/i18n/routing.ts`，无手写副本；`sitemap.i18n.locales` 用 `LOCALE_META` 的 `htmlLang`（`en` / `zh-CN`）
- `sitemap.filter` 排除 404，`serialize` 用 `src/lib/seo/lastmod.ts` 写逐页 `lastmod` 并补 `x-default`；`contentGuard()` 把两个校验脚本挂进构建生命周期
- `public/_redirects` 不配置 SPA fallback（不写通配 200 rewrite），避免任意路径返回 200
- `process.env.CI === 'true'` 或 `process.env.REQUIRE_REAL_DOMAIN === '1'` 时，`site` 仍为 `example.com` 会直接让构建失败
- `base` 保持默认 `/`：当前方案使用 Pages 自定义域的根路径。框架本身支持子路径（`absoluteUrl()` 与 `robots.txt` 按 `BASE_URL` 拼接），但本方案不使用

### 8.4 构建脚本

脚本定义以 `package.json` 的 `scripts` 为唯一来源，此处不复制。`deploy` 先用
`npm run build` 产出完整的 `dist/`，再用 Wrangler 部署到 Cloudflare Pages；
完整命令与环境配置见 `deploy/cloudflare/README.md`。
质量门 = `npm run validate && npm run check && npm run test`（提交前自查），
发布时 `npm run build` 内的构建守卫已重复覆盖其中两项，无需另跑。

`scripts/build-guard.mjs` 以 Astro integration 的形式挂在 `astro:build:start` 与 `astro:build:done`：
前者执行内容体检；后者按 `LOCALES` 把 `dist/<前缀>/404/index.html` 复制成 `404.html`
（Pages 按前缀就近查找错误页），再检查产物内链。因此**直接执行 `astro build` 也不存在绕过校验的入口**，
且产出的 `dist/` 无需额外步骤即可上传。
Cloudflare Pages 以 `npm run build` 为构建命令、`dist/` 为产物目录，云端构建跑的是同一条流水线
（需完整 git 历史，逐页 `lastmod` 依赖 `git log`）。
`validate` 与 `check-links` 单独可用，分别用于提交前自查与产物复检。

`validate-content.mjs` 的检查项：

| # | 检查 | 失败级别 |
|---|---|---|
| 1 | 标题长度（含后缀后、按显示宽度）与全站唯一性，覆盖内容集合与 `src/data/pages/entries/*.ts` 页面级文案 | 错误 |
| 1.1 | 页面条目路径唯一、格式合法（小写、首尾斜杠；大写会在大小写不敏感的文件系统上互相覆盖） | 错误 |
| 1.2 | 页面条目的导航 `order` 在同一区内唯一（主导航、页脚各分区分别比对） | 错误 |
| 1.3 | 标题/描述的重复填充桩与截断痕迹（`src/lib/seo/copy.ts` 的 `findTitleIssues` / `findDescriptionIssues`）；占位词 `hasPlaceholder` 只告警 | 错误 / 警告 |
| 2 | 描述长度 | 错误 |
| 2.1 | 译文 `seoTitle` / `seoDescription` 的长度与唯一性（`checkLocalizedSeo`，逐语言） | 错误 |
| 3 | 型号编码 slug 与文件名一致 | 错误 |
| 4 | 所有 `reference` 字段指向的条目存在，含 `guides` / `faqs` 的 `related*` | 错误 |
| 5 | 品类对比表的每一列，在该品类每个型号的 `keyParams` 中都有同名键；**按语言各查一遍**（译文只翻一半时整列渲染成「—」） | 错误 |
| 6 | `datasheet` 与 `downloads.file` 指向的物理文件存在 | 警告 |
| 7 | 集合没有已发布内容（仅 `applications` / `cases` / `guides` / `faqs` / `downloads` 五个集合） | 警告 |
| 7.1 | `guides` / `faqs` 的每个 slug 在每个语言下都有文件；同语言不得有两个同 slug 文件；正文不得为空 | 错误 |
| 7.2 | 参数型集合整块缺译或 `REQUIRED_TRANSLATION` 必填字段缺失（`checkTranslation`） | 错误 |
| 8 | 产物中的站内链接目标存在；`PENDING_ROUTES` 登记的路径仅警告 | 错误 / 警告 |
| 9 | 各语言页面一一配对（经 `parsePath`/`localizePath` 动态配对，不写死语言前缀）；单语言页面须登记在 `SINGLE_LOCALE_PAGES` | 错误 |
| 10 | 型号/品类 `image` 指向的文件在 `public/` 下存在 | 错误 |
| 11 | 任何 `<img>` 必须带 `width`/`height`/`alt`/`loading`（扫描前屏蔽注释） | 错误 |

另有 `tests/` 下的 Vitest 单测（`npm run test`，8 组：routing / branding / copy / content / nav / dict / text / check-links）——
它们测的是「规则本身」，规则错了校验层不会发现。

第 5 项是实际踩过的坑：品类声明了 `IP Rating` 列，型号的参数键写的是 `Protection`，对比表渲染出来整列是空的——**构建不报错、页面看得见，只有人工逐页检查才会发现**。这类「数据能渲染但没对上」的问题，schema 管不了，只能靠跨条目校验。

第 6 项只警告不拦截：`datasheet` 与 `downloads.file` 常滞后于内容录入，`existsSync` 判断的结果仅为告警，不应阻断整个站点发布；`downloads` 列表项按 `file` 字段直链，文件缺失需运营按同名补传。

标题后缀、长度区间、页面级文案与 slug/字符计数规则不在脚本里重复定义，而是从 `src/data/*.ts`、
`src/lib/seo/branding.ts` 与 `src/lib/utils/text.ts` 直接导入（Node 24 原生类型擦除），避免脚本与运行时的规则漂移。

任一项错误即中断构建。**这是「约束前置」原则的落地点**——不合格的内容进不了产物。
